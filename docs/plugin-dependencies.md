# 插件依赖与 Python 视图：标准

本文是**标准**：它规定依赖属于谁、插件与它的字节存在哪、视图怎么生成、生命周期按什么判据走、迁移按什么顺序做。后续实现以本文为准。

[当前架构](architecture.md) 记录"当前实现进度"；本文与它不一致时以进度为准，但**不得改变本文的不变量**。[依赖环境与资产闭环：设计决定与方案复核](dependency-environment-draft.md)（ADR-001）里"环境名字 + 内容寻址 + 每 run 冻结绑定"的模型**已被本文取代**，该文件只作历史与"为什么推翻"的记录。

本文所有内容都是**已定的决定**，不是待批准材料；只有最后一节"开放问题"列出的内容未定。文中不声称任何东西已经实现；尚未开始的部分见最后一节与[开发台账](pilot-development-plan.md)。

## 背景与动机

推翻旧模型有三个根因，不是"实现没做好"。

**① 依赖放错了所有者。** 依赖属于**插件**。旧模型把依赖声明挂在 Graph 节点的 `environment` 名字上，再由 Library 的部署级名字表把"名字 → 环境编号"变成平台资产。结果是：插件作者真正要说的事（这个插件需要哪些包）没有所有者，平台却多了一等公民"环境"，还要处理它的准备、检查、发布、绑定、更新、回退和删除。

**② 为补①造了一整套形式主义。** 为了让"环境"这个名字可信，旧模型加了：全树内容 SHA-256 当编号、不可变发布、部署级名字表与 CAS 切换、接纳期解析一次、每 run 冻结 `{使用位置, 名字, 编号}`、每次节点调用前复核发布树指纹、把 venv 物化成"自己的"（去掉全部符号链接、复制解释器）。这套机制自洽，但它服务的对象来自①。代价是一层独立管线、Run 记录格式迁移、同一个原因在三处映射成三种错误类，以及反复的回归与审查。

**③ 同一个需求重复批准会复制整套环境。** 编号是**发布树全树内容**的 SHA-256，而装机工具会往树里写时间戳。实测：`dist-info/uv_cache.json` 的内容只有时间戳，文件长度随 `nanos_since_epoch` 的位数变化；两棵只差这次批准的树除该文件外逐文件相同，编号却不同。于是同一个需求再来一次，同一批包又存一份，空间白白翻倍。

结论：依赖的正确所有者是插件；平台只需要**共享存储 + 每个插件版本一份视图**。本文守住这件事。

本文另外守住两件事（这两条推翻了此前"每 run 钉住视图快照"的路线）：

- **run 不钉任何东西。** 节点调用永远用**当前**那一份插件；升级从下一次节点调用起立刻生效。理由：插件（代码 + 数据）世界上一份，钉住就等于要求平台保留历史副本、在 run 记录里冻结绑定，还要为"有人在跑"设计确认与回收——它们服务的是"怕升级"；真正需要的是让升级**诚实、及时、可查**。
- **平台不预测插件的行为，只提供机制和接口。** 插件自己知道哪些路径是它的数据（清单里声明），平台只提供：一个家、一份视图、一次复制。

**先前的实测事实**（真实机器，用于支撑下面的不变量与硬约束）：

- 共享缓存下把同一个包装进两个视图：`--link-mode=hardlink` 下是**同一 inode**（一份字节）。uv 0.11.6 在 Linux 的默认是 `clone`（reflink，XFS 上共享 extent；`du` 看不出来，`df`/`fiemap` 才准）。
- 视图 A 装 `idna 3.7`、视图 B 装 `3.6`：两个进程各读到自己的版本；两个视图的 `bin/python` 都是指向 `/usr/bin/python3.12` 的符号链接（解析后 sha256 相同）。
- **同一个进程**里硬把两个 `site-packages` 塞进 `sys.path`：出现"版本号报 A、子模块属于 B"的假模块 → 一个进程只能一个版本。
- **符号链接视图可用**（`import` 正常、`sys.prefix` 正确指向视图），前提是视图自带 `pyvenv.cfg`；缺它则 `sys.prefix=/usr` 且 import 失败。硬链接视图与 `.pth` 视图同样可用。

**为什么不能靠"进程生命周期"钉住（背景，不是主要论证）**：bwrap 0.4.0 + xfs 实测，`--ro-bind` 是**同一个 inode 的挂载**，不是内容快照。源目录一旦被 `rm -rf`，挂载它的进程再往里看就是**空目录**（`os.listdir` 返回 `[]`、懒加载 `ModuleNotFoundError`、打开文件 `FileNotFoundError`），只有已经 import 进内存的模块对象还活着。这条事实的用处是排除一个选项——"挂载自然就把旧版本钉住了"不成立。它**不是**本模型不要快照的主要理由（主要理由是上面那两条决定）。

## 术语表

| 术语 | 一句话 |
| --- | --- |
| 插件 | 平台的可复用能力单元，自带清单、工具和依赖声明；**代码与数据同在插件目录里，世界上一份**。 |
| 插件目录 | 那个唯一的家：库根的 `plugins/<id>`。运行时按 id 只在这里找插件，没有第二条路。 |
| 依赖声明 | 插件清单里写的"我要哪些包、什么约束"，由插件作者负责，不属于节点或 run。 |
| 可变路径 | 清单顶层 `"mutable"` 显式列出的、由插件自己在运行时改写的路径；平台只提供位置，不读、不校验、不复制、不重写。 |
| 代码摘要 | 覆盖可变路径之外内容的 SHA-256；用来认"这份代码是哪一份"，**只对代码**。 |
| 共享存储 | 平台级目录，按（包、版本）存放解包后的字节；所有视图从这里取文件，字节只有一份。 |
| 视图 | 每个插件版本一份的轻量 Python 环境：一个 `pyvenv.cfg` 加指向共享存储的指针，决定该插件进程能 import 到什么。 |
| 清单 | 记录"哪个 run 从第几步起**实际**用了哪个视图、里面是哪些包版本"的观察事实。 |
| 回收 | 删除共享存储里不再被任何已装插件的视图指向的**包版本**——只有这一类。 |

术语刻意不用"树""指纹"作为核心概念：视图就是"一个 `pyvenv.cfg` + 一组指针"，需要确认内容时直接读文件，而不是拿一棵内容哈希树当身份。也刻意不再有"run 快照"与"reload"两个概念：前者被"永远用当前那份"取代，后者在"永远用当前那份"之后无事可做。

## 不变量

后续 agent 必须守住以下各条；每条都能被检查。

1. 依赖声明属于插件，不属于节点或 run。
2. 平台共享存储里，每个（包、版本）的字节只存一份。
3. 每个插件版本一份视图：一个 `pyvenv.cfg` + 指向存储的指针；`bin/python` 指向同一个系统解释器（"一个 Python 只一份"）。
4. 同一进程只能看到一个版本的同一个包（Python 硬边界）；多版本共存靠视图，因为视图的单位是进程。
5. 安装/升级插件时，宿主用 uv 按**该插件自己的声明**求解并落地到视图；解不出来 = 报错原文抛给人（插件内部冲突不是平台责任）。
6. **run 不钉任何东西**：节点调用永远用**当前**那份插件（代码 + 视图）；升级从**下一次节点调用**起立刻生效；已完成的步骤不回滚、不重放。变了之后出问题，由 agent 自己调整。
7. **升级随时允许，不需要任何确认或提示**，也不因为有人在跑而禁止。
8. **回收只剩一类字节**：共享存储里的某个（包、版本）没有任何已装插件的视图指向它，才可删除。**不存在"插件代码版本"这一类**——插件只有一份（不变量 13），平台不留历史代码。
9. 插件代码与数据在同一个目录里，靠清单声明区分：**平台只替换代码，绝不复制、重写或校验清单声明为可变的路径**；插件摘要只覆盖代码。
10. 清单（这个 run 从第几步起实际用了哪个视图、里面是哪些包版本）保留；它是**观察记录**，不是"钉住"的承诺，也**不承诺能复现历史**。
11. Python 能力由插件提供；graph 不声明环境，run 记录不含环境绑定。
12. 执行仍在**无网沙箱**里；包只从**部署授权的来源**获取（沿用现有的公网/回环与哈希校验策略）。
13. **插件只有一份**：家在库根的 `plugins/<id>`；导入时从源复制一次，此后**图包只带引用**、不留历史版本、不跨机器复制。

## 生命周期

各阶段写清触发点、判据和失败行为。所有会改共享存储或视图的操作（安装、升级、卸载、回收）共用**同一把写锁**。

### 安装（导入）

- **触发点**：人导入一个插件。
- **动作**：源 → 暂存 → 校验清单与代码摘要 → 原子落入 `plugins/<id>`。**这是唯一一次复制**（不变量 13）。随后宿主用 uv 按该插件自己的依赖声明求解 → 从部署授权的来源取包（沿用现有抓取与哈希校验）→ 落地到共享存储（按（包、版本）去重）→ 为该插件版本生成视图。
- **失败行为**：求解失败报 uv 原文给人；取包失败按既有授权来源规则报错，不做静默回退。两种情况都**不装、不改任何已有视图、不动已有插件目录**；暂存丢弃。
- **审批**：这是人要批准的那一次，见"审批面"。

### 升级

- **触发点**：导入同 id 的新的代码（或人批准该插件的新依赖声明）。
- **判据**：**不**看"有没有 run 在跑"（不变量 7），**也不弹任何确认或提示**（不变量 7）。
- **动作**：**只替换代码**——清单声明为可变的路径原地不动，既不复制也不重写也不校验（不变量 9）。代码替换落定后，新代码若声明了新的依赖，为它生成自己的新视图；旧视图不删，交给回收判据。正在跑的 run 从**下一次节点调用**起就用新代码 + 新视图。
- **失败行为**：求解失败即拒绝这次升级，旧代码与旧视图不动；取包失败同理。**回滚范围只有本次代码替换这一步**——数据自始至终没有被碰过，所以不存在"回滚数据"这回事。
- **并发**：与安装、回收共用同一把写锁。

### 运行

- **触发点**：节点调用某个插件（本地进程/工具）。
- **判据**：**当前**安装的那一份插件，按插件 id 在唯一的家里（`plugins/<id>`）找；**没有第二条解析路径**（没有"图目录优先""catalog 优先"这类回退）。
- **动作**：按当前那份的声明把该插件进程指向它当前的视图；挂**插件目录本身**。
- **失败行为**：视图缺 `pyvenv.cfg`、或视图指向的存储内容缺失 → 报错说明事实；不静默回退到别的视图。
- **升级发生在 run 中途**：不需要任何特殊处理——下一次节点调用自然就是新代码 + 新视图；已经完成的步骤不重跑，也不因为"代码变了"而拒绝继续。

### 卸载

- **触发点**：人卸载插件。
- **动作**：删插件目录与它的视图；顺手跑一次回收扫描。没有历史版本可留，所以"删插件"等于把代码**与数据**一起删掉——**这一点尚未定**，见"开放问题"。
- **失败行为**：删不掉要如实报错，不静默当作已卸载。

### 回收

- **触发点**：升级、卸载时顺手扫；与安装共用同一把写锁。
- **判据**：不变量 8——共享存储里的包版本没有任何已装插件的视图指向它，才可删。
- **失败行为**：判据不成立就不删；判据拿不准时按"保留"处理。**不存在"非终态 run 的快照"这一类保护对象**——run 用的是当前那份，升级与回收都不动它。

## 边界与硬约束

- **插件只有一份**（不变量 13 的展开）：家在库根的 `plugins/<id>`；图包只带**引用**，绝不嵌插件字节；不留历史版本；不跨机器复制。源那边自己有没有副本、要不要留，不归平台管。
- **代码与数据在同一个目录里，靠清单声明区分**：清单顶层 `"mutable"` 是字符串数组，每项是插件目录内的相对路径（以 `/` 结尾表示整个子树），显式列出**插件自己会改写的路径**。平台只替换代码，绝不复制、重写或校验这些路径；**摘要只覆盖代码**——可变路径一直在变，无法按摘要认，也不该被校验。
- **单根部署的例外，写在这里**：标准部署有三个根（`BUNDLE_ROOT` 是图包、`CATALOG_ROOT` 是图目录、`LIBRARY_ROOT` 是插件家），包内出现 `plugins/` 一律非法（那是旧形状，加载器拒绝并提示重新导出）。**唯一的例外是单根部署**：部署把库根目录本身当图包目录（`CATALOG_ROOT`/`LIBRARY_ROOT` 与 `BUNDLE_ROOT` 指向同一处，开发脚本与多数测试就是这样）时，那里的 `plugins/` 是库自己的插件家，不是包携带的插件字节——加载器必须由调用方显式告知库根（`with_library_root`）才放行，**不告知即拒绝**。库根本身只有一处导出（`ANCHOR_RUNNER_LIBRARY_ROOT`，其次 `ANCHOR_RUNNER_CATALOG_ROOT`，再退到本次配置的图目录），**不从包路径猜**：只设 `ANCHOR_RUNNER_BUNDLE_ROOT` 的部署没有插件家，插件相关操作具名拒绝，而不是把插件装到包旁边。
- **挂插件目录本身，不挂它的父目录**：实测挂父目录时，正在跑的进程会直接看到新内容与兄弟目录，挂载面被放大；插件只能看到自己的目录。
- **一个进程一个版本**：Python 没有"进程内多版本同名包"这回事；多版本共存只能靠"每插件版本一个视图 + 一进程一视图"。
- **视图必须自带 `pyvenv.cfg`**：缺它会导致 `sys.prefix` 塌回 `/usr` 并 import 失败（实测）。生成视图时必须写这个文件。
- **准备区与存储必须同一个文件系统**：真正需要同设备的是"准备区 → 存储"的**原子改名**（`rename` 不跨设备），跨设备会失败。视图与存储之间**不**需要同设备——视图用的是符号链接，跨设备照样可用（硬链接才要求同设备，我们不用硬链接）。因此：启动时校验准备区与库根同设备（不同即拒），**不**要求视图与存储同设备。
- **同一插件内部依赖冲突**：只能拒绝安装，或把插件拆成两个进程（各自一份视图）。平台不替插件内部的和解负责。
- **无网**：执行在无网沙箱里；联网只发生在宿主侧按部署授权来源抓包的那一步，沿用现有的公网/回环、无凭证、不跟随跳转与哈希校验策略。
- **视图与存储不是可写环境**：插件进程不得写共享存储、也不得写别的插件的视图；插件自己的数据写在插件目录里它声明的可变路径下。

## 审批面

- 人批准的是**导入/升级这个插件**：装什么插件就批准它带来的那批包。表单展示求解结果（包与版本、来源）与这个插件被哪些图引用。
- **升级就是升级，不再有第二次确认**：此前"有 N 个未结束的 Run 正在使用这个插件、升级会让它们失败"的搁浅提示删除。表单**如实说明**"升级从下一次节点调用起对正在跑的 run 生效"即可，这句话不是确认门槛。
- 旧模型里"批准一个环境"的入口（环境需求单、环境发布/准备表单、名字表切换）随旧模型一起删除：这些内容现在是插件的属性，跟着插件导入走。
- 批准永远不是工具参数；未确认不执行。

### 要改的

- **安装/升级的整树原子替换 → 只替换代码**：可变路径既不复制也不校验；对 `plugins/<id>` 不再用整目录 `RENAME_EXCHANGE`（那会把数据一起换掉）。原子性下沉到代码条目，见"开放问题"。
- **`plugin.json` 字段白名单要加 `mutable`**：`rust/anchor-graph-host/src/dependencies.rs` 现在会拒收不认识的字段；`mutable` 必须是声明，不是被拒的笔误。
- **run 记录里的 `plugin_bindings` 降级为观察记录**：如实记下本次调用实际用的插件代码摘要与视图，供人查看，不再充当阻断判据（也不再有"冻结绑定"的含义）。
- **清单/时间线**：如实记录"这个 run 从第几步起用了哪个视图、里面是哪些包版本"，不再阻断。

### 要加的

- **共享存储与视图生成**：按（包、版本）落地字节；每插件版本生成 `pyvenv.cfg` + 指针 + 指向同一系统解释器的 `bin/python`。
- **每插件求解**：uv 按插件声明求解，不引入"环境"这个对象。
- **导入的"复制一次"**：源 → 暂存 → 校验代码摘要 → 原子落进唯一那个家；此后平台不再复制插件字节。
- **`mutable` 声明与"只替换代码"**：清单显式声明可变路径；升级只换代码。
- **回收**：按不变量 8 的判据扫（只有包版本一类），与安装共用写锁。

## 迁移顺序

原则是**先建后删**：新路径跑通前不拆旧的，避免"两边都不能用"的中间态。每条都要给出可验收的证据形式——真实执行过的命令与输出，不能用"接口存在"或"小样例通过"代替。

1. **最小垂直切片**（已落地，见台账）：一个内置 python 插件声明依赖 → 插件安装时 uv 求解 → 装进共享存储 → 生成视图 → 该插件的工具在无网沙箱里真的 import 到声明的包。
   *证据形式*：安装命令的输出里能看到求解结果与视图路径；沙箱内一条命令打印出被声明包的 `__version__`，而宿主 PATH 与系统解释器都取不到它。
2. **升级即刻生效 + 插件只有一份**（**这一条比原计划小得多**）：导入只复制一次；图包只带引用；运行时只剩"按 id 找唯一那个家"这一条解析路径；删掉搁浅确认与"changed since Run admission"类阻断（降级为如实记录）；`mutable` 声明与"只替换代码"。不做回收，不删旧模型。
   *证据形式*：同一个 run 的第一次节点调用打印 `idna 3.6`，升级插件的依赖声明后第二次调用打印 `3.7`——同一个 run、没有重新接纳、没有被拒绝；记录里能看到它从第几步起换了视图；`bundles/<graph>/` 下 `grep -r` 不到插件字节；升级期间另一个在跑的 run 正常结束。
3. **回收 + 清单**：回收按不变量 8 删除**包版本**（只有这一类）；清单能回答"这个包版本被谁用""这个 run 从第几步起用了哪个视图"。（原第 3 条 reload 删除：永远用当前那份之后，reload 没有对象。）
   *证据形式*：回收前后共享存储的文件数与字节数；只有"没有任何已装插件视图指向"的包版本被删，仍被视图指向的一字节未少。
4. **整片删除旧机制**：做完前三条再整片删除旧机制，并核对没有代码路径还在调用旧机制。

## 社区参照

| 参照 | 借什么 | 不借什么 |
| --- | --- | --- |
| Spack | 唯一存储 + 符号链接视图；同一包多版本并存 | 包定义 DSL 与自有构建体系 |
| Nix/Guix | `/nix/store` + 链接 profile 的"一份字节、多视图"形状 | 内容寻址的环境身份、用构建输入给环境命名 |
| 容器镜像 / overlayfs | 只读层 + 合并视图 | 镜像作为分发与冻结单位 |
| uv `--link-mode` | clone/reflink 或 hardlink，落地时共享同一份字节 | 不另做平台自己的安装器 |

我们借用"一份字节、多视图"这个形状，**不**引入形式化的内容寻址"环境"概念：存储按（包、版本）组织，视图只是一组指针。

## 开放问题

以下是**未决定**的事，实现时确认，不要当成已定：

- **卸载是否连数据一起删**：插件的数据就在插件目录里它声明的可变路径下，删插件目录就是删数据。代码只有一份、没有历史版本，所以"只删代码、留数据"不是一个可选项；平台要不要在卸载时保留、导出或先询问，未定。
- **只替换代码时的原子性**：可变路径原地不动之后，整目录 `RENAME_EXCHANGE` 不再可用，原子性下沉到每个代码条目；一次升级中崩溃可能留下"部分新代码 + 部分旧代码"。要不要更细的提交/回滚协议，未定。
- **准备区与库根跨设备**：`rename` 不跨设备，此时准备区无法原子落入存储。本切片按 fail-closed 处理（启动即拒），是否要支持跨设备部署尚未定。
- **插件进程生命周期**：本仓库目前是"每次节点调用"组装/启动进程；升级即刻生效之后，常驻进程与每 run 的语义要在实现时确认（常驻进程会看到被换掉的代码）。
- **升级即刻生效与 MCP 工具集重协商**：插件工具清单变化时怎么重协商，没定。
- **清单存哪**：进 run 记录、独立文件还是只读投影，没定。
- **python 插件的能力边界**：要不要限制它能在自己的视图里做什么（装包、改 `pyvenv.cfg`、写存储），没定。
- **旧数据的处理**：磁盘上已有的 `library/envs/`、`names.json`、图包里已有的插件副本，以及格式 9/10 的 run 记录是留、是迁、还是只读保留，没定。
