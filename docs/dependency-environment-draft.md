当前已有工具路径登记与沙箱接线，但没有把“一套可复用依赖”作为独立资产管理的契约。本文暂称其为**依赖环境**：供工具运行或构建复用的解释器、工具链、可执行文件和库。凭据、节点权限与可写工作区属于其他事实，不混入这个概念。

## 已确定的决定（2026-10-10 用户确认，已复核）

以下记录的是已确认的目标设计，均尚未完整实现；它们与下文现状核查没有冲突。

1. **真身位置。** 环境内容存放在 Library 根下，与插件同一个根：`library/envs/<编号>/`。环境与插件一起备份、一起检查、在一处看全。
2. **引用写名字，事实记编号。** 节点和工具写一个人可读的组合名（例如 `research`）；Library 持有名字表，记录“这个名字当前解析成哪个编号”。新 Run 准入时解析一次，并把 `{使用位置, 名字, 编号}` 一起写进 Run 事实。后续执行、暂停、恢复和进程重启直接使用已冻结编号；名字留作解释来源，不重新解析。
3. **更新/回退切换名字，版本内容不可变。** 新版本先构建、验证并发布为独立编号，再将名字指向这个**已经存在**的编号；回退指向此前已发布的编号。名字表切换只影响之后接纳的新 Run，不覆盖或修改旧编号目录。删除仍受引用保护，但“解除名字”和“删除版本文件”必须区分：前者检查依赖该名字的 Graph/Plugin/工具声明，后者检查名字表、保留 Run、已冻结资源绑定与活动进程是否仍引用该编号。删除操作的具体入口留待裁定；不能以删除一条名字记录代替物理内容的引用检查。
4. **一个组合一份，不是一节点一份。** 一批节点需要同一实际依赖组合就复用同一编号。仅一个节点需要额外依赖时，准备一个新的组合名并调整该节点的引用，其他节点的引用不变。若选择更新大家共用的名字，则所有之后引用该名字的新 Run 都会使用新版；已有 Run 继续旧版。变更需展示影响范围，新组合与受影响路径仍应验证，不能笼统承诺“不需要重测”。

本节保留已确认的存放、名字/编号、共享与不可变原则，并补充其执行含义。删除入口、环境身份算法、批准方式与持久化迁移仍待设计，空缺列在文末「待裁定项」。

例如 `research → E1` 时接纳的 Run 保存 E1；名字后来切换成 `research → E2`，该 Run 重启后仍挂载 E1，新 Run 使用 E2。运行路径不能通过可变的 `current` 链接寻找依赖。若 E1 缺失或不匹配，应报错并说明事实，不能改用 E2。因此名字表切换与“重启不跟随 current”完全一致。

## 已明确的产品目标与优先级

用户要求：Anchor 独立部署后，用户能通过 Pilot 管家完成平台全部 Graph、Plugin 和依赖环境的管理与调整。管理覆盖完整生命周期，不能只交付安装按钮，再让用户通过宿主 Shell 手工维护依赖。

| 管理对象 | 需要覆盖的能力范围（目标，尚未完整实现） |
| --- | --- |
| Graph | 查询、创建、编辑与组合、校验、资源绑定、版本更新/回退、删除，以及独立包导入/导出 |
| Plugin | 查询、获取/创建/适配、工具与资源自测、依赖与配置调整、安装/更新/回退/卸载，以及凭据授权入口 |
| 依赖环境 | 需求声明、解析与冲突诊断、构建/复用/验证、绑定、更新/回退、引用查询与清理 |

第一优先级是多 AgentNode 的依赖环境拥有唯一事实来源，跨节点、跨 Graph 复用，避免人工为每个节点或 Plugin 管理一份 venv。概念保持语言无关，首个可验证场景聚焦 Python。新目标取代旧范围中的“自动环境安装暂缓”；实际构建、发布与资源使用仍通过 Host 的授权契约。

当前对 Pilot 自身 Graph/Plugin 的自升级保护是已有边界。完整管理目标下，如何由用户通过 Pilot 发起受控调整、验证与交接，需要单独明确；不能通过直接写正在使用的资源目录来绕过保护，也不在本稿中决定热切换语义。

## 现有三个 environment

| 名字 | 当前含义 | 与依赖环境的关系 |
| --- | --- | --- |
| `SandboxEnvironment` | 一条子进程环境变量，包含 key/value | 可以传递配置，但不表示一套依赖 |
| `ToolEnvironment` | Host 读取所有 `tools/<id>/tool.json` 后汇总的只读挂载、工具目录和 imports；用于沙箱授权与请求接线 | 已有加载与接线能力，没有独立环境的身份、版本或生命周期 |
| `tool.json.environment` | 可选的绝对前缀目录；entrypoint 必须位于其中，存在 `bin/` 时加入工具搜索路径 | 是依赖载体路径，不能据路径确定内容版本 |

`tool.json` 已声明 `entrypoint/environment/imports`，工具目录也已有 ID，因此不能说“完全没有声明或名字”；缺少的是**独立依赖环境的声明与内容身份**。`imports` 会作为只读路径挂载，也会在未显式设置时组成 `PYTHONPATH`。

目前每个节点的独立 workspace 不等于每个节点已有私有 venv。`ToolEnvironment::load` 汇总整个工具目录，`apply` 将汇总结果加入节点命令、Op 和 stdio MCP 请求；没有按节点或 server 选择并冻结依赖环境。因此接入不能仅在现有全局 PATH/imports 上叠加缓存。

入口与挂载机制不限 Python，但实现仍有 Python venv 符号链接和 `PYTHONPATH` 兼容逻辑。Rust、Node、JVM、conda 等环境能否使用，还取决于目录布局、路径授权和所需运行配置；本次没有运行这些环境，不能把通用入口能力写成逐语言验收结论。代码依据：[Sandbox 契约](../rust/anchor-runtime/src/sandbox.rs)、[工具环境接线](../rust/anchor-runner-host/src/tool_environment.rs)。

## 用同一组四步核对三类资产

**声明 → 冻结身份 → 授权 → 引用**：分别回答“包含什么”“是哪一份”“谁允许什么”“执行实际用了哪一份”。这是概念核查维度，不表示三类资产已有统一协议或相同生命周期。

| 资产 | 声明 | 冻结身份 | 授权现状 | 执行引用 |
| --- | --- | --- | --- | --- |
| Graph | 作者 JSON | Run 接纳时保存 `GraphSnapshot` 与 `graph_digest`；删除确认另绑定准确目标及资源前置条件 | Host 校验管理权限；Pilot 删除需要原生确认，新建/更新当前没有统一的原生确认步骤 | Run 保存冻结 snapshot 与 digest |
| Plugin | `plugin.json`、Skill、MCP 与资源目录 | 内容 digest，资源随 Graph/Run 冻结 | 操作员安装；当前工作区新增 Pilot 候选审查、原生安装确认与内容变化守卫，表单到安装端到端尚未验收 | Run 的 `PluginBinding` 保存 id、digest、资源与 server 名称 |
| 依赖环境 | Graph 节点的 `environment` 名字；Plugin 侧 `anchor.environment` 逐 server 声明 | **内容指纹与不可变发布**（`library/envs/<编号>`），名字表带版本号与 CAS 切换；Run 接纳时把名字解析成编号并冻结**带使用位置的绑定** | 操作员命令（`anchor-library env …`）；还没有 Pilot 申请、批准计划或自动准备入口 | 节点任务与 Plugin stdio server 都走同一套：Run 冻结绑定（按使用位置）→ 执行请求 → 沙箱按发布路径只读挂载并复核；HTTP/SSE MCP 不继承本地环境 |

Graph/Plugin 的冻结记录可见 [Run 事实](../rust/anchor-runtime/src/graph/state.rs) 与 [PluginBinding](../rust/anchor-runtime/src/graph/ports.rs)。Plugin 确认路径属于当前未提交工作区，验证边界见 [开发台账 A159/A160](pilot-development-plan.md)，不能据此宣称已部署或真实 provider 已跑通。

缺口也包含实际内容的一致性：**沙箱只读挂载不等于宿主内容不可变**。现有 Graph/Plugin 摘要不覆盖登记在外部前缀与 imports 中的依赖内容，因此现有 Run 记录不能证明接续或重启后仍使用同一份依赖。仅增加摘要，也不会自动保证后续执行使用原内容。

**实现状态（2026-10-10）。** 已交付“身份与发布”层（位于 `anchor-library`）与“节点级执行绑定”层（Host 接纳、Run 格式 10、两条执行路径挂载与复核）。操作员命令如下：

```sh
anchor-library --root <Library> env publish --directory <准备好的目录>
anchor-library --root <Library> env list | show --id <编号> | verify
anchor-library --root <Library> env name set <名字> --id <编号> [--expect-version <版本>]
anchor-library --root <Library> env name remove <名字> --expect-version <版本>
```

语义与本文决定一致，并经一轮独立复核后收紧：

- **编号** = 发布树内容的 SHA-256，覆盖条目名（按原始字节，不做过 UTF-8 转换）、目录条目、文件的可执行/可读位与文件内容。**写位不参与身份**，因为发布必然清除写位；因此"同一内容"指发布后的字节与模式相同。空目录与可执行位都是身份的一部分，不会被复用吞掉。
- **发布**先整体去写位、仅在 rename 前给顶层留写位、落位后立刻再去写位（内核移动目录时要更新其 `..`）；随后对整棵树做 fsync，并区分"发布成功"与"发布后保护/持久化不确定"。已发布目录从不就地修改。
- **复用会修复**：`publish` 命中同一编号时会重新施加只读，并在需要时重新计算，所以"同 owner 把权限改回去"之后不会把可写树当成合格发布。
- **名字表**原子替换，名字切换/解除都是**名字版本 compare-and-swap**；`name remove` 必须提供观察到的版本，不提供就不允许删除。表出现本版本无法完整表示的字段时拒绝读写，不会静默截断既有绑定。
- **`env verify`** 重新计算每个已发布环境的指纹，并报出：指纹不符、`envs/` 里的意外条目、名字指向的不是编号或指向缺失内容、以及**已发布内容仍可写**；有问题时以非零退出，"检查跑不起来"也是失败。
- **读操作不需要写权限**：库不存在时 `list`/`verify` 返回空而不是创建目录，因此加固部署（独立 owner 或只读挂载）下 `env verify` 仍可运行。
- **节点级绑定已接线（2026-10-10）**：Graph 节点可声明 `environment` 名字；接纳时由 Host 解析成已发布编号并冻结进 Run 记录（格式 9）；执行请求携带该绑定；该节点的命令只挂载这一个已发布环境（**按发布路径只读挂载**，因此 venv 内部的绝对引用仍然有效），PATH 只加它的 `bin`，**不再继承全局工具聚合**。未知名字、内容缺失或指纹不符一律拒绝接纳；旧格式记录迁移后不带任何环境身份，恢复也从不重新解析名字。命名表的解析只发生在接纳时。
- **两条执行路径都已接线**：AgentNode 的工具路径与 OpNode 的命令路径共用同一个挂载函数；`Op.run` 一开始漏接，被 Host 端到端用例抓到并已修复。Host HTTP 入口的端到端用例已补：声明的环境被解析、执行时真实挂载（命令只有在环境内文件存在且内容匹配时才成功）、Run 记录携带 `{名字, 编号}`；未知名字在接纳时被拒且不创建 Run。
- **独立复核后的收紧（2026-10-10）**：①只有 `Op.run` 能声明环境——`call`/`fanout`/`join`/`host` 节点声明会在快照校验时被拒（否则会冻结一个永不挂载的绑定，`call` 更会让子 Run 静默退回旧聚合）；②**记录的编号在每次节点调用开始前复核**，已发布树与记录不符时拒绝运行（不再"路径同名即通过"），恢复同理；③授权面收窄为"只授权该 Run 冻结的那些树"，不再整库授权；④其余 Run 创建路径（会话、常驻助手、独立宿主入口）在写任何持久事实**之前**解析环境，失败则不落任何孤儿事实；⑤子 Run 在本层无法解析环境，因此**在持久化之前拒绝**——要支持子图使用环境，需要把环境存储下沉到更低的层（见下）。
- **架构审查（独立，2026-10-10）结论与处置**：
  1. **事实必须带使用位置**（审查：#2 优先）——已实施：Run 格式 **10**，`environments` 以规范化站点键索引（`node_task:<节点>`，切片 2 起为 `plugin_server:<节点>/<插件>/<server>`），值里带类型化站点；9→10 迁移从旧节点键恢复站点、**不发明身份**；校验要求"键与站点一致、站点属于存在的节点、名字等于该站点的声明"，并要求**每一处声明都有冻结绑定**（声明未冻结即视为损坏）。`NodeExecutionRequest` 现在携带该节点的全部站点绑定，并提供 `task_environment()` / `plugin_server_environment()` 两个访问器，避免各路径各自猜。
  2. **存储层位置造成子图死路**（#1）——**死路已解，未搬仓库**：采用了审查提到的"端口"这一半——`anchor-graph-host` 定义 `EnvironmentResolver`（`freeze(snapshot, plugin_bindings)`），宿主提供基于 `EnvironmentStore` 的适配器并在构造 Op.call 宿主时注入；子 Run 因此能冻结自己声明的环境，且父 Run 与子 Run 共用**同一个**冻结实现（含逐 server 站点解析与 HTTP/SSE 不继承环境的规则）。存储位置保持不变：端口已经解掉死路，把读侧单独拆成新 crate 的价值从"解死路"降为"命名与契约更清晰"，因此**延后**，等切片 2 执行侧落地后再评估。宿主未配置解析器时子图仍是明确拒绝，且拒绝在任何持久子事实之前；配置了会话交接的调用，远程授权可能已在拒绝前发生，这一点如实写在代码注释里。
  3. **部署根被反复从环境推导**（#3）——**未实施，已定方向**：在入口解析一次 `DeploymentConfig`，经 `RunApplication → PreparedExecution → HostNodes → ToolEnvironment` 传递；`LIBRARY_ROOT` else `CATALOG_ROOT` 只在一处定义。当前失败是 fail-closed，"库根不符"会被执行前复核挡住，因此记为债务而非现网缺陷。
  4. **每次调用整树重算指纹**（审查建议改）——**暂留但记账**：现有实现是每次节点调用前复核一次（不是每命令），代价是 O(树) 同步读；审查建议改为"接纳 + 每 Run 一次 + 依赖部署层的所有者/只读挂载保证"，且**不做抽样/限时哈希**（那是虚假信心）。这条在切片 3 之前重审，因为它与部署加固方案绑定。
  5. **读写契约未分离**（审查建议）——与第 2 条一起做。
  6. **明确不建**：环境的删除/回收与引用保护、继续扩大操作员 CLI、通用环境构建平台、把 HTTP-MCP 排除建成事实（缺失绑定 + 校验规则更小且不会漂移）。
- **接线时暴露并修掉的潜在缺陷（2026-10-10）**：`stdio_config` 对**绝对路径**的 command/args 做了插件相对映射（`plugin_directory.join(绝对路径)` 恰好又等于绝对路径且宿主上确实存在，于是被拼成 `/plugins/<id>/<绝对路径>`）。此前只有工具环境的 entrypoint 映射在后面"救回来"，所以没有暴露；受管环境不使用那一层映射，问题立刻显形。现在绝对路径的 command 与 args 一律原样透传，相对路径才按插件资源映射。这属于既有缺陷的修复，不是新功能的附带改动。
- **授权模型最终收口（2026-10-10，架构审查后）**：Run 政策回到"部署底线"（工作区、产物、允许命令、网络、目标命名空间），**所有按 Run 决定的挂载都在调用时授权**：冻结环境、插件目录、本地输入都用同一套宿主 grant。此前存在两种机制并存（政策预授权 + 调用授权），并且迁移只做了一半——**插件目录的授权被删掉而没有被搬过来**（架构审查发现的回归，已修并补两端用例）。适配器的方法也按性质改名：`with_tool_dirs` → **`with_executable_dirs`**，因为授权的目录不只是进 PATH，还允许其中的命令绕过部署的 basename 白名单（这正是冻结环境能提供自己解释器的原因），文档与代码现在都写明这一点。
- **每调用的授权模型（2026-10-10 收口）**：冻结环境在沙箱里表达为**这一次调用的宿主授权**（grant），而不是政策里预授权的一堆编号——因为 Run 的政策在构造时还不知道它将来会调用哪些图、那些图会声明什么环境。请求里仍然带挂载项与 PATH 项，适配器因为已有对应 grant 而接受这一对；于是父图与子图用**同一套**机制，政策保持最小（不需要整库授权），PATH 仍然只来自该次调用冻结的那一份。适配器因此新增 `with_tool_dirs`（与既有 `with_readonly_grants` 同一性质：宿主为一次调用授予权限，而不是请求索取）。
- **PATH 与「不静默回退」的准确含义（2026-10-10，正确性审查后）**：受管调用里 PATH 是**冻结环境的 `bin` 在前、部署的系统目录在后**，所以「该环境提供的名字一律解析到该环境」成立；但「PATH 里只有环境」并不成立、也不打算成立——`sh` 这类宿主外壳仍来自系统目录。为守住「不静默回退到其他解释器」，现在要求：**已发布环境必须有 `bin/`**（否则它提供不了任何命令，却会被记录成「用了它」，直接拒绝）；并且**宿主不会启动的 server（`anchor.fake`，或缺少可选环境变量而被禁用）如果在清单里声明了环境，直接拒绝整次调用**，而不是留下「记录了却没用上」的绑定。
- **已记录的边界**：①被调用图（子 Run）**可以**声明环境：`anchor-graph-host` 定义 `EnvironmentResolver` 端口，子 Run 接纳时向宿主解析并冻结；宿主没有配置解析器时**明确拒绝**，且拒绝发生在任何持久子事实（`/in/call` 包、子记录）之前；②`call`/`fanout`/`join`/`host` 节点不能声明环境（快照校验拒绝）；③声明环境**替换**全局工具聚合，因此"用我的 venv 同时用操作员登记的工具"目前做不到；④`tool_environment` 只认 `LIBRARY_ROOT`、没有 catalog 回退，只设 `CATALOG_ROOT` 的部署会解析出环境但得到空的工具聚合。
- **被证伪并已修正的声明**：①曾有「PATH 只来自该次冻结的那一份」的说法，实际 PATH 仍包含部署系统目录（见上条：已按真实语义改写，并补上两处 fail-closed 检查）；②文档曾称"读操作不再需要写权限"（加固部署下 `env verify` 仍可运行），但读路径实际用 `O_RDWR|O_CREAT` 打开锁文件——现在读路径改为**只读打开已有锁文件并取共享锁**（没有锁文件即视为没有发布），并新增"把锁文件与 `envs` 目录设为只读后仍能 `names/show/list/verify`"的用例。
- **结构性收口（2026-10-10，按两次独立审查）**：①**冻结遍历只在内核一处**（`anchor_runtime::graph::freeze_environments`），父接纳、子 Run 接纳与记录校验不再各自实现遍历，加第三种使用位置时不会只改一处；②**端口缩成一次名字查询**（`EnvironmentResolver::resolve(name) -> id`），站点归属由内核决定，实现者只需回答「这个名字现在指哪个编号」；③**权限表**：Pilot 工具的权限收成一张表（`Inspect`/`Mutate`/`Confirm`，12/6/3），定义、只读标记与分发都由它派生，并有「确认类工具集合 == 交互层自己的名单」这条不变量测试——这样「批准永远不是工具参数」是结构性质，而不是一句描述；`Mutate` 中六个还没有原生表单的工具作为**已登记债务**保留。**2026-10-10 第三轮审查后的收口**：①记录校验改用同一个 `declared_environment_sites`（不再自己遍历一遍），因此「冻结、校验、影响范围报告读同一份声明清单」现在是真的；②启动器用类型化的 `PluginServerId` 作键（`SandboxLaunch.server_environments`），不再手写 `<插件>/<server>` 字符串；同时明确：规范化键 `EnvironmentSite::key()` 以 `/` 连接，而 Plugin id 与 server 名（`valid_reference`）不允许 `/`，且校验要求 `from_key(key)` 必须还原出该站点本身，否则拒绝——手工构造的「一个键满足两个声明」的记录因此不可能通过。权限表更新为 **13 Inspect / 7 Mutate / 5 Confirm**（`environment_provision` 加入后为 5），并新增独立的 `effect` 轴（`Read`/`HostFact`/`Asset`/`Execution`/`Control`，断言 `Inspect ⟺ Read`），因此「只有资产需要人点一次」是表上的不变量，「Mutate 里没有原生表单的工具」仍是登记债务但不再把需求单算作审批债务。
- 仍未实现：uv 构建与沙箱 builder（受授权的环境准备是唯一还没闭合的产品能力）；发布计划与批准流程、Pilot 的只读/需求/发布工具**已交付**（见第 3 条）。仍未决：文档化的 `LIBRARY_ROOT` 路径只在部署模板里显式设置，还没有以它为准的端到端用例（当前用例走的是 catalog 根的回退路径）。
- 独立复核后仍开放的项：候选树的遍历仍是按路径解析（文件用了 `O_NOFOLLOW`，目录仍是 lstat→read_dir），理论上存在目录被替换的竞态；没有清理/隔离损坏编号或残留准备区的子命令（`verify` 只报告）；写保护仍是信号而非边界，真正强制靠部署层。

## 待对齐的概念边界

Graph、Plugin、依赖环境都可以作为可复用资产讨论；Run 控制、计划、会话与查询主要是在既有授权内使用或管理能力。资产变更会增加、替换或删减长期可用能力，“永久扩大能力”不足以覆盖更新与删除。准备、检查候选与发布已安装资产也是不同阶段。

“三类资产变更都由人确认”是待讨论的目标原则，目前没有全面实现。普通操作是否需要额外确认应沿用各自的权限和效果契约，不能从这个分类推出免授权，也不应把内部恢复事实变成新的用户审批流程。

本文暂用“依赖环境”，英文名与现有类型/字段的最终命名未定。概念身份、前缀路径、环境变量和 Host 加载器应能明确区分；`Runtime Environment` 是否易与 Runtime 配置混淆，可在概念对齐后一起决定。

## “环境指针”方案评估

推荐方向是**共享解释器与包产物、按实际依赖组合复用不可变环境、节点持有宿主解析的环境引用**。节点可写工作区继续独立。这里的唯一事实来源指宿主持有权威的已发布环境清单与安装身份；物理文件复用是另一个目标，不能以缓存目录代替产品事实。

| 层次 | 含义 |
| --- | --- |
| 需求声明 | 作者或 Pilot 表达需要什么，包括版本约束；不是运行时的确切版本事实 |
| 已发布环境 | 固定解释器构建、选定包产物与安装结果；可被多处复用 |
| 执行绑定 | Run 保存节点任务环境及需要的 Plugin server 环境的确切引用 |
| 下载/构建缓存 | 加速准备，允许清理与重建；不拥有 Run 身份 |

相同解释器构建、目标平台和实际安装组合应复用一个环境。相同兼容包产物尽量共享文件或数据块；不同版本、ABI、平台或构建输入可以产生不同产物。环境仍有少量私有元数据与入口脚本。这里没有“全平台一个可变 Python 环境”的要求，也不承诺所有文件物理上永远只有一份。

方案需保留以下语义：

1. **依赖按进程组合。** 同一 Python 进程需要一起 import 的包联合解析；不同 stdio MCP server 可以使用不同环境，并共享底层解释器和包。Plugin 的服务器依赖不自动合并进节点任务环境。多个需要 Python 的 Plugin 也不意味着多份人工维护配置。
2. **冻结实际使用的环境。** 相同 `uv.lock` 可以因 extras/groups、平台、安装策略和构建输入产生不同环境；宽泛的 `Python 3.12` 也不是解释器构建身份。应记录选定产物和实际安装结果，不能只 hash 顶层包名或锁文件。
3. **升级不改变已有 Run。** 依赖变更产生新环境；新 Run 接纳新版。旧 Run 的暂停、恢复、invocation 和进程重启继续引用旧版，不能在重启时跟随 `current` 链接切换。常驻实例的版本交接沿既有退役/新实例边界讨论。
4. **所有写入路径遵守不可变。** 只读 bwrap 挂载保护节点，但宿主也不得对已发布环境执行 install/sync 或修改共享包。硬链接共享 inode，不能让缓存或其他环境中的写入影响已发布内容；写时复制则有不同的写入语义。环境和解释器清理必须保护保留资产、Run 与活动进程的引用。
5. **复用成熟工具。** uv 可承担解析、锁定和安装，bwrap 继续承担隔离，Anchor 保存身份、授权、发布与执行绑定。执行普通节点时使用已准备环境，不临时联网求解或静默回退到其他解释器。构建原生包、系统库闭包和离线独立部署须有明确支持边界。

本次实际执行 `python3 .local/research_dependency_environments/uv_reuse_probe.py`，使用 uv 0.11.6、已有 Python 3.12.13、生成的纯 Python wheel、隔离缓存、offline 与显式 hardlink：两个不同依赖组合中的同版本模块具有相同 device/inode，另一版本独立，三份 venv 指向同一解释器；清除实验包缓存后仍分别导入正确版本。证据位于 `.local/research_dependency_environments/uv-probe-upl5q6_c/evidence.json`。这只验证 uv 的局部复用机制，没有经过 Anchor Host、Goose、bwrap、真实 provider、原生包或独立部署，不构成功能交付。

首个环境切片应验收：跨 Graph 多节点共享同一确切环境；冲突需求形成独立组合或明确报错；新版本发布后旧 Run 及重启恢复保持旧引用；无关缓存清理不破坏已发布环境；用户能经 Pilot 准备、验证并绑定环境。上述是建议验收方向，具体清单、身份算法、确认方式与持久化迁移仍待设计。

这里“经 Pilot 准备”应包含：用户表达依赖需求，Pilot 发起宿主受授权的解析/构建/复用动作，校验通过后发布并绑定。环境登记 CLI 可以是实现过程中的内部步骤；如果最终仍要求用户登录宿主手工创建 venv，则尚未达到本次管家目标。自动准备的 uv 接线属于这条目标路径，原生包等支持边界可分阶段扩展。

### a：批准完整计划，发布核对结果

“包与原因”不足以绑定最终内容。计划应包含具体解释器构建、实际安装集合（含传递依赖与 extras/groups）、选中 wheel 的来源和 hash、安装策略，以及目标名字和它当前的编号。部署者的源白名单是权限前置条件，不能替代内容锁定。

一次确认授权 Host 按该计划准备、验证、发布并执行明确的名字切换。准备结果与计划不一致，或候选/目标在等待期间变化，就停止并返回具体原因；不能自动扩大许可。计划指纹与最终环境内容编号各有用途，不能只凭声明摘要推定安装内容已经吻合。无需为一个未变的计划重复询问构建和发布。

### c：三处声明承担不同职责

| 位置 | 保存什么 | 不承载什么 |
| --- | --- | --- |
| Library 环境清单 | 依赖组合、锁定结果、解释器与实际产物身份 | 不维护另一张“所有节点使用哪个环境”的反向权威表 |
| Graph 的 AgentNode / `Op.run` 节点 | 一个任务环境名字引用（字段名候选 `environment_ref`） | 不重复依赖清单、不自动继承角色或全部 Plugin 的依赖 |
| Plugin 的 Anchor 运行声明 | 按 stdio server 名称绑定环境名字 | 不把它混入 MCP `env` 键值对，不让 HTTP MCP 继承本地环境 |
| Run | 展开后的节点、任务/工具/Plugin server 使用位置、声明名字和解析编号 | 不在恢复时重新选择名字当前所指的版本 |

Plugin 的 server 绑定可放进 `plugin.json` 的 Anchor 扩展区，并纳入 Plugin digest 和冻结资源；具体 JSON 字段尚未定。不应直接在标准 MCP 配置里塞一个含义不同的 `env/environment`：当前 [`validate_mcp`](../rust/anchor-graph-host/src/lib.rs) 会拒绝未知 server 字段，`env` 已明确是环境变量表。独立 `/tools/<id>/run` 的环境引用也应归其工具声明，保留旧 `tool.json.environment` 路径兼容边界，但不能把它当作已冻结的环境引用。

接入时，Host 从 Run 绑定为每个进程选择对应挂载、解释器和 PATH，不再把全部登记依赖汇总进受管理进程。Graph 作者编译、资源校验、`GraphRunRecord`、`NodeExecutionRequest` 和 stdio 启动契约需一起对齐；稳定契约只表达通用环境身份，不依赖 uv 或 Python 实现。已有 [`GraphNode`](../rust/anchor-runtime/src/graph/model.rs)、[节点字段白名单](../rust/anchor-runtime/src/graph/authoring.rs)、[执行端口](../rust/anchor-runtime/src/graph/ports.rs) 与 [stdio launcher](../rust/anchor-runner-host/src/tool_host.rs) 都尚未支持这些新字段。

### d：写保护必须覆盖准备者，发布不得覆盖旧版

新版本内容的发布和名字表切换是两件事。先验证并使内容可用，再按预期旧编号切换名字；切换失败时保留可核查结果，不能暴露指向未完成内容的名字。若编号已存在，核对后复用，内容不匹配则拒绝覆盖。

所有任务和构建进程都只能读已发布内容；构建只写自己的准备区。普通 `chmod` 不能单独防止同一 owner 改回权限，也不能防止共享硬链接的另一条路径被写入；实现必须覆盖所有可写入口，并验收实际写入拒绝。共享解释器及其可变别名也在保护范围内。venv 的脚本/解释器链接可能带绝对路径，不能未经验证将临时目录 rename 后就视作可运行发布。

Run 引用应按一次稳定接纳视图解析并持久化。删除检查与新 Run 接纳、活动进程使用必须协调，避免“刚查到无人引用，另一个 Run 已接纳，文件却被删除”的窗口；复用现有 Host/Library 的事实与锁边界，不为此新增通用垃圾回收或恢复平台。

### 复核回合 3：按复核修正后的结论（2026-10-10）

上一轮的三条新增与四条精确化已按复核修正；修正处标注“修正”。a–d 至此没有遗留分歧，可进入 ADR 定稿。

**协调与锁（修正上一轮的错误措辞）**

上一轮把 `catalog_read_guard`、`graph_catalog_mutation_guard` 与 Run 接纳说成“同一把锁”，与代码不符。现状是三套不同机制，保护不同事实：

| 机制 | 实际是什么 | 保护的事实 |
| --- | --- | --- |
| `Library::catalog_read_guard` | `plugins/.install.lock` 上的跨进程 `flock`（共享/独占） | Library 插件目录的安装与读取 |
| `RunApplication::graph_catalog_mutation_guard` | Host 进程内的 tokio mutex | 进程内 Graph catalog 变更 |
| `RunApplication::graph_admission_lease` | 按图不可变身份取得的 `RunLease` | 某个图的接纳与运行 |

因此：影响范围报告只能是**派生视图**；提交切换、删除或接纳时需要**版本号加 compare-and-swap 式重检**，不能靠复用其中某一把锁。方案与仓库里已有的两个受守卫操作同构——图删除用“前置条件 + 内容未变守卫”，插件安装用“审查指纹 + 未变守卫”。具体建议：名字表带版本号，切换/解除/删除以“我看到的版本来提交”，提交时版本已变就拒绝并要求重新确认。人等待期间**不得持锁**，提交前必须重检。

**构建在哪里跑（修正措辞）**

构建命令在 bwrap 沙箱里执行；Host 负责解析、编排、核对与发布。措辞不应写成“Host 永远不执行工具”——现有 Git checkout 已经是 Host 侧的受控适配器。准确说法是：**不在 Host 直接执行不受信任的构建与安装过程；可信的部署适配器可以按自己的契约执行固定命令。**

构建只能写专用准备区，已发布环境对它不可写，网络使用部署授权，沿用超时与输出限制。

**bootstrap 不能形成循环。** 首个 uv/python bootstrap 由部署包提供、固定版本并校验 digest；以后可以登记成环境资产，但不能要求它先由自身构建出来。

**解析期的联网（修正）**

需要授权，但**不需要第二次用户确认**：部署配置预先规定允许的源与镜像；Pilot 只能请求解析，不能让模型指定任意外网地址。解析产生的计划、源范围、请求者与计划 digest 要留事实；下载内容只进入临时准备区或缓存。用户一次确认具体计划后，Host 再下载并安装；hash 或源发生变化就停止。

现状提醒：bwrap 目前只有 `NetworkPolicy::Enabled` 这一总开关，**没有源白名单或代理范围**，所以这是待实现的权限扩展，不能写成现成能力。

**legacy `tool.json`：显式双模式（取代上一轮的“新字段优先”）**

- 没有新字段：按 legacy 路径模式运行；
- 有 `environment_ref`：按受管环境模式运行；
- 两者同时出现：**拒绝并要求迁移**，不静默猜优先级。

legacy Run 至少记录 legacy 模式、工具 ID、解析后的路径与当时观察到的身份；单写 `global` 或 `tool:<id>` 不构成环境身份。受管进程也不得偷偷继承旧的全局 PATH/imports 聚合。旧路径先兼容；等官方 Plugin 与示例全部改成显式引用后，再关闭新安装中的隐式路径。迁移流程为：Pilot 扫描旧路径 → 发布受管环境 → 修改声明 → 重新确认安装。

**发布布局（修正）**

准备目录与发布目录同父、执行 rename，**不足以**保证 venv 中的绝对 shebang、`pyvenv.cfg` 与解释器路径仍然有效。要求改为：构建时就使用稳定的最终运行路径，或者发布后完整验证并处理所有绝对路径；**单次 import 成功不算验证**。

**`current` 的使用规则（写硬）**

`current` 只允许用于新 Run 接纳时解析。Run 的执行、暂停、恢复、重启与删除检查，都只使用已保存的环境编号，不再读取 `current`。旧 Run 没有环境编号时，也不能事后解析当前名字来补造身份。

**两条仍然成立的精确化**

- **名字是部署级命名空间。** 一个 Library 一张名字表，名字是唯一字符串；创建、切换、解除都走同一次批准；名字不能由图名、节点名或插件名自动派生，否则改名会连带改依赖。
- **绑定变更就是资产变更。** 把环境名字写进 Plugin 清单（进 digest）或图节点（进 snapshot），意味着改名字等于改资产：插件要重新安装确认、图要重新保存校验。这是“绑定可追溯”的代价，不是缺陷。

### ADR 应记录的边界

正式 ADR 应明确：Library 内容/名字与 Run 使用事实的归属，批准计划及发布前置条件，作者字段与 Plugin server 选择，名字切换/删除与接纳的并发规则，以及新 Run 格式和旧记录的兼容方式。旧 Run 没有保存过环境编号时，不能事后解析当前名字并冒充原环境身份。环境缺失/漂移的反馈及常驻实例版本交接也应明确。uv 的离线实验继续只作为机制证据，实际完成状态仍由开发台账记录。

裁定后，应把结论写进上文「方案需保留的语义」与「首个环境切片应验收」两节；在此之前不要把上面的候选当成已接受的设计。

## 实施契约（2026-10-10 定稿，供实现对齐）

本节把 a–d 的决定翻成实现必须遵守的契约。改动跨 Kernel 与 Host，**必须一次对齐，不能先加字段再补行为**。

**五个改动点（缺一不可）：**

| # | 位置 | 改什么 |
| --- | --- | --- |
| 1 | Graph 作者格式与编译（[节点字段白名单](../rust/anchor-runtime/src/graph/authoring.rs)） | 节点新增可选的环境名字引用（候选字段名 `environment`，名字须是合法标识符）；未声明的节点行为不变 |
| 2 | Plugin 清单的运行声明（[`validate_mcp`](../rust/anchor-graph-host/src/lib.rs)） | 每个本地 stdio server 可选绑定环境名字，放进 Anchor 扩展区，纳入 Plugin digest 与冻结资源；不与标准 MCP `env` 混用 |
| 3 | Run 事实（[`state.rs`](../rust/anchor-runtime/src/graph/state.rs)） | 保存每个使用位置解析出的 `{使用位置, 名字, 编号}`；恢复只读这份事实 |
| 4 | 执行请求（[`ports.rs`](../rust/anchor-runtime/src/graph/ports.rs)） | `NodeExecutionRequest` 携带本节点及其 server 的冻结绑定，执行层不自行再解析 |
| 5 | 宿主接线（[`tool_environment.rs`](../rust/anchor-runner-host/src/tool_environment.rs)、[stdio launcher](../rust/anchor-runner-host/src/tool_host.rs)） | 按冻结绑定选择挂载与 PATH；受管进程**不得**再继承旧的全局工具聚合 |

**不变量：**

1. **失败关闭。** 声明的名字在接纳时无法解析、内容指纹不符、或同时出现 legacy 路径与受管引用，一律拒绝这次接纳并说明原因；不降级、不回退、不临时安装。
2. **记录即所用。** Run 记录里的编号必须是这次执行真正挂载的那一份。在没有真正接线的阶段，宁可拒绝接纳，也不允许出现"声明了但没生效"的记录。
3. **不补造历史。** 旧 Run 没有环境事实时保持没有；恢复时若记录的编号缺失或内容不符，报错说明事实，不改用当前名字指向的版本。
4. **只读且只增。** 执行只读挂载；环境内容不可变；改版本 = 发布新编号 + 切名字。
5. **绑定即资产。** 节点字段进图快照、server 字段进 Plugin digest，改绑定等于改资产，走各自的确认路径。

**Run 格式与兼容：** 新增环境事实需要 Run 记录格式升级；旧记录按"没有环境事实"解码，不解析当前名字补写。格式版本号与迁移写法按现有 `FileRunStore` 的既有模式处理，并在迁移测试中固定"旧记录不被改写"。

**切片顺序（每片都必须能独立验证）：**

1. **节点级任务环境（已交付，2026-10-10）**：改动点 1、3、4、5 中与节点任务环境相关的部分。验收已覆盖：声明了环境的节点，其命令只能看到该环境的挂载与 PATH，看不到其他已登记工具环境（真实 bwrap 差分用例）；名字未知/内容不可用时接纳失败（接纳解析用例）；未声明的图行为不变（全量回归 523 项）；Run 记录与恢复沿用同一编号（记录校验与 8→9 迁移用例）。Host HTTP 入口的端到端 Run 已覆盖（触发真实 Run，命令仅在环境内文件存在且内容匹配时成功）。
2. **Plugin server 级环境（已交付执行侧，2026-10-10）**：改动点 2 与 5 的 server 部分。已覆盖：同一节点下不同 stdio server 使用各自冻结的环境（按 `<插件>/<server>` 站点取绑定，逐 server 授权自己的 `bin` 与挂载）；受管 server **不再继承**全局工具聚合；HTTP/SSE 传输不涉及本地挂载，因此不会继承本地环境（校验仍然只对 stdio 声明做解析）。**仍有缺口**：①"Plugin 绑定变化触发重新确认"依赖切片 2 的安装/审批流程，未做；②受管 server 的**恢复**路径（Run 记录里的 server 站点在恢复时重新核对指纹）有执行前复核覆盖，但还没有专门的恢复用例。
3. **Pilot 只读与申请**：先能看已发布环境与名字表，再给「需求单 → 一次确认 → 受授权准备」的路径；CLI 仍是内部步骤。　**【只读、受确认的发布、需求单与影响范围已交付（2026-10-10）；受授权的自动准备未做】** 只读：`environment_list` 与 `environment_show`（按 `name` 或 `id`，宿主**重新核对指纹**后才描述内容）。受确认的发布：`environment_publish` 是权限表里的 `Confirm` 类工具——模型只能给工作区内的候选目录和要指向的名字，**批准永远不是工具参数**；宿主先算出候选内容身份（与 `publish` 同一套 staging）、记下名字当前指向与版本，把**计划记录**写进 `state/environment-plans/<身份>-<名字>.json`（写于弹表单之前），再用原生表单让人点一次；批准后宿主**重新核对内容身份与名字版本**，一致才发布并切换名字（名字表 CAS），不一致就拒绝且不改动任何东西；拒绝或取消把计划标为 `Refused`，**待批计划不会自动重放**（明确不是队列）；管家不能改自己的依赖——它自己的图或其插件的 server 声明用到这个环境名字时，工具直接拒绝，让它找操作员。**两轮审查后的收紧**：①身份校验发生在**内容可见之前**（`publish_expecting` 在拷贝后、rename 前比对，因此「批准的树」与「被发布的树」不可能不同，也不再多拷一遍）；②`already_published` 只有在**名字指向该身份且内容仍能核对通过**时才为真；③候选没有 `bin/`、或落在 Library 内，都会在弹表单之前被拒；摘要改为 `spawn_blocking`，不再阻塞运行时线程；④计划写入改为唯一临时名 + 文件与目录 fsync；⑤失败/取消/回合结束都会把计划终结为 `Aborted{原因}`，**已批准但没做成的事不会读成「没人回答」**；⑥只读投影 `GET /environment-requests` 区分 `published`（带 `id`）与 `requested`/`refused`/`aborted`（`id` 为空、`digest` 始终是当时看到的内容）。**需求单与影响范围**：`environment_request`（`Mutate`，只写自己的持久需求）把「要什么环境、为什么、解释器约束、包名」记成按名字唯一的 `state/environment-requirements/<名字>.json`；`environment_references`（`Inspect`）给出**派生**影响范围（哪些图的哪些节点/插件 server 用到这个名字，含内联模块图；不存反向索引，读不到的图以计数暴露），发布表单在点确认前显示它。只读投影分为 `GET /environment-publications`（发布计划）与 `GET /environment-requirements`（需求）。**仍未做**：需求被满足后的自动对账通知、以及计划/需求记录的清理策略。**受授权的自动准备（uv 构建那一层）已在同一轮交付**，见下一节。

### 第三轮审查后补记的决定（2026-10-10，A179–A180）

这些是清理提交做出的、此前 ADR 没有记录的选择：

- **投影的读取容错只用于只读投影**：`list_json_records` 跳过读不出的记录并计数（`unreadable`），排序**之后**再按上限裁剪并报告 `truncated`；两个只读投影（`/environment-publications`、`/environment-requirements`）都报这两个数。**决策读取一律严格**：名字表、发布前置条件与 CAS、需求状态派生都不容忍跳过——「读不出」绝不能变成「没有」。
- **影响范围报告的候选集**是「可编辑图目录 + 本部署配置的那一个 bundle」，逐图通过 bundle 加载器编译后读内核的声明清单；加载不了的图进 `coverage: Partial{considered,total,missing:[{graph,reason}]}`（带原因），目录读不到是 `Unknown{reason}`。报告**不再**自己解析可编辑 JSON，也**不再**把 `ANCHOR_RUNNER_BUNDLE_ROOT` 当「装 bundle 的目录」扫（那会让配置在目录根之外时报告假 `Complete`）。它是接纳语义（编译后的节点 id、bundle 自带的插件）而不是编辑语义，因此「暂时编辑坏了的图」会显示为缺口而不是悄悄消失。
- **两个身份是刻意的**：记录里用 `EnvironmentSite::key()` 字符串键（serde_json 的 map 键必须是字符串，且格式 9 的旧记录用裸节点 id），启动器用类型化的 `PluginServerId`。`site` 字段仍存在（键可读、便于按站点回答「这个 Run 用了什么」），其一致性由校验保证。
- **`EnvironmentError::Writable` 是接纳级拒绝**：`show`（接纳前调用）拒绝「已发布但重新可写」的树；操作员视角用 `describe`（返回 `writable` 标志而不拒绝），只读工具 `environment_show` 走 `describe`。
- **每次节点调用仍复核指纹**，只是搬到 `spawn_blocking`，不再阻塞运行时线程。仍未做：**接纳期**解析名字时的 `show()` 整树哈希仍在运行时线程上（与 `digest_candidate` 已异步化不对称）。
- **发布计划按「一次批准」建身份**（`digest + name + session + turn`）：同一候选同一名字的两次批准不再互相覆盖终态；表单展示过的**影响范围会写进计划记录**并出现在只读投影里（此前是只写不可读）。
- **错误分类按原因**：Run 已记录的环境事实无法兑现 → `GraphError::CorruptRun`；接纳期解析不出名字 → `GraphError::Unsupported`；工具边界 → `String`。宿主内部统一为类型化的 `Unusable`，并在 A185 拆成 `Recorded`/`Unconfigured` 两类 + `into_graph_error()`：**AgentNode 路径不再把同一条件重标成 `Unsupported`**——原因穿过了原先的 `String` 缝（`ResolutionError::{Graph, Host}`），现在与 `Op.run` 对同一条件给出同一分类。
- **仍未做的结构项**：`prepare`/`describe` 的整树哈希与 `list` 的描述成本（**接纳期**已在 A185 移出运行时线程：父 Run 的冻结与子 Run 的端口调用都在阻塞线程上）。`pilot_tools` 已按族拆开（A186：`graphs`/`runs`/`plugins`/`sessions`/`environments` 各自成模块，表仍在 `pilot_tools.rs`）。
- **记录保留（A185 决定）**：`state/environment-plans` 与 `state/environment-provision-plans` 每个名字最多保留 20 条（含待批）；
  **待批永不删**，只删最旧的**终态**记录，**读不出的记录不删**；记录带 `created`（旧记录为 0，按最旧处理）。已发布内容的写保护仍是部署边界。

### 批准请求的生命周期（设计卡 001，2026-10-10 批准并实现）

计划记录在弹出原生表单**之前**落盘为 `Requested`，因此"人还能不能回答"必须与它一起被表达清楚。四项已批准并实现的决定：

- **取消有独立终态**：新增 `Cancelled{reason}`（两个家族），与 `Refused`（人在表单里答"否"）和 `Aborted`（人批准了但事没做成）**分清**——终态不得发明人的决定。
- **`already_published` 早退留痕**：内容已发布时写 `Published{observed_id, observed_name_version}`，不留一条"看起来还在等人回答"的请求。
- **保留只删可证明冗余的记录**：按 `(名字, 候选身份)` 分组，只保留**最新终态**与**最新成功记录**；`Requested`、读不出的记录、以及名字当前可能指向的那条**永不删除**。删除数累加进家族级旁路计数（只增不减，非 `.json`），并在 `/environment-publications` 与 `/environment-provisions` 里报为 `pruned`。**取舍**：同一候选的重复尝试有界，不同候选之间不删（"每名字 20 条"的硬上限被明确否决），因此一个名字下的不同候选仍会累积，投影侧继续由既有的 200 上限 + `truncated` 约束。
- **过期的请求在启动时收尾**：`recover_pilot_turns` 用平台会话事实（`TurnStatus`，`Running` 之外即无人能答）把遗留的 `Requested` 记录就地写成终态；顺序是先 `interrupt_running()` 再收尾，所以宿主崩溃遗留的 `Running` 也在内。
- **表单已返回答案、但回合在这件事执行前结束**（实施期间发现的第四条早退路径）：按**已知答案**写终态——批准了则 `Aborted`，否则 `Refused`，**不写 `Cancelled`**（人已经回答）。这条路径的到达状态由端到端用例确定性覆盖（测试客户端在交回答案前用同一个会话存储把 Turn 置为 `Stopped`，`active()` 真的失败）；`select!` 在"答案就绪 + 取消同时置位"时的随机 tie-break **本身**未被确定性覆盖，两条路径进入的是同一段处理代码。

### 批准账本删除（设计卡 002，2026-10-10 用户决定 A「删除干净」）

上一节（设计卡 001）以及本文「实施契约」「受授权环境准备的实现决定」里所有关于**计划记录**的内容，均被本节取代：宿主不再把批准状态写进 `state/environment-plans/` 与 `state/environment-provision-plans/`。`EnvironmentPlanStatus`/`EnvironmentProvisionStatus`、`write_*_plan`、`abort_*`/`cancel_*`/`settle_abandoned_*`、`prune_environment_records`/`Retention`/`RecordList`/`pruned.count`、两个只读投影（`GET /environment-publications`、`GET /environment-provisions`）及其映射全部删除。理由是收敛准则：那是在平台会话的 `Question` 之外维护的第二本账，每加一处都要付「两本账必须一致」的利息，而同一事实只应由一个所有者持有。

- **权威所有者只剩两处**：「人被问过什么、答了什么」是平台会话的 `Question`（宿主只读）；「发布了什么内容、名字指向哪个编号」是 Library（已发布树不可变 + `names.json` CAS）。宿主自己拥有的 `state/environment-requirements/<名字>.json` 保留。
- **批准不再落盘**：两个 precondition（发布候选的内容身份/名字/观测版本；准备路径解析出的锁定集合）只存在于**本次调用**的内存里；跨重启不重放因此是结构性质，而不是一条需要维护的规则。
- **不变量照旧，且仍在本次调用内判定**：批准不是工具参数；未确认不执行；发布前由 `publish_expecting` 复核内容身份（与批准时一致），不符即拒；名字切换仍是 `observed_name_version` 的 CAS。
- **旧文件不动**：磁盘上已有的计划文件宿主不再读也不再写，留给操作员自行处置（不是本卡的清理任务）。
- **后果（如实记录）**：两个跨会话只读投影被删。它们展示的事实仍可从 Library 列表与会话提问路由（`GET /sessions/{s}/turns/{t}/questions`）看到，但「把所有批准历史汇到一处」的视图没有了；要找回它，正确做法是让平台给 `Question` 打类型标签（改 `anchor-platform-session`），而不是在宿主里再记一本账——本卡不做。

## 受授权环境准备的实现决定（2026-10-10，A182）

**联网边界（用户裁定，2026-10-10）**：构建沙箱**永不联网**——适配器在没有 `allow_network` 的策略上构造，因此一个请求即使写了 `NetworkPolicy::Enabled` 也会被拒绝（有专门用例）。联网只发生在**宿主侧可信适配器**：它按部署授权的源解析与抓取，产物落到准备区，随后沙箱只从那里离线安装。这比「给沙箱开网络 + 源白名单」更强：不依赖被执行的工具自觉遵守代理。

**部署配置（缺一即拒；全部由操作员设定，模型与图都够不着）**：

| 变量 | 含义 |
| --- | --- |
| `ANCHOR_ENVIRONMENT_SOURCES` | 逗号分隔，每项是绝对目录（`--find-links`）或 http(s) 简单索引（`--index`）。只给目录时解析加 `--no-index`，不会偷偷查 PyPI |
| `ANCHOR_ENVIRONMENT_UV` + `ANCHOR_ENVIRONMENT_UV_SHA256` | 固定的 bootstrap 工具，**每次使用前复核 digest**（bootstrap 不自我循环） |
| `ANCHOR_ENVIRONMENT_PYTHON` | 基础解释器；其身份（版本、路径、prefix、二进制 digest）进计划 |
| `ANCHOR_ENVIRONMENT_BUILD_ROOT` | 准备区（默认 `<state>/environment-build`），永远不是已发布内容 |

只设了一部分 → 启动即失败；一个都不设 → 本部署不准备环境，`environment_provision` 明确拒绝并说明原因。网关/模型都不能提供地址。

**五步，各有边界：**

1. **解析**（宿主，联网）：`uv pip compile --generate-hashes --only-binary :all: --no-header --no-annotate`。**来源白名单是边界而不是约定**：uv 的 `--index` 是"附加在默认索引之上"，所以第一个授权索引必须用 `--default-index`（替换默认索引），其余才用 `--index`；只给目录时用 `--no-index`。解析子进程 `env_clear()` 后只注入 PATH/HOME/UV_CACHE_DIR/UV_PYTHON_DOWNLOADS 并把 CWD 设为准备区，否则 `UV_INDEX`/`PIP_INDEX_URL`/代理/TLS 变量或上层的 `uv.toml` 都能把源集合悄悄放大（2026-10-10 独立审查实测：修复前，授权索引对某包返回 404 时 uv 会去 pypi.org 取回真实摘要写进计划）。锁定文本与工作目录无关，因此同一需求得到同一身份；包名先按严格字符集校验（不接受 `-` 开头、路径、URL、marker），避免写进 `requirements.in` 的文本被当成选项。
2. **抓取**（宿主，联网）：按 PEP 691 JSON 找**哈希相等**的产物；索引与产物 URL 复用宿主已有的出站 URL 策略（公网地址、无内嵌凭证、**不跟随重定向**）；落盘时边写边算 SHA-256，不符即删。索引因此只是投递手段，不是权威。**只抓 wheel**：真实锁定文件会同时记录同版本 sdist 的哈希（实测 `idna==3.7` 就是 wheel + tar.gz 两个哈希），而安装 sdist 意味着现场编译，所以非 wheel 一律拒绝——这让"不编译源码包"成为结构性质，而不是"取决于索引恰好提供了什么"。抓取是**异步**接口：阻塞式 HTTP 客户端会自建 runtime，在 runtime 线程上析构会 panic（实测），异步化让调用方不可能踩到这个坑。
3. **构建**（沙箱，**无网络**）：`uv venv --relocatable` 与 `uv pip install --no-index --find-links … --require-hashes`，环境变量固定为 `UV_OFFLINE=1`、`UV_NO_CACHE=1`、`UV_PYTHON_DOWNLOADS=never`、`UV_LINK_MODE=copy`。挂载与 PATH 都来自**这一次调用**的授权（策略层只授权固定的 `uv` 目录与准备区）。
4. **物化**（宿主）：Library 只接受普通文件与目录，而 venv 到处都是符号链接。最后一步把树变成它自己的：`bin/python` 成为**计划里那个解释器的副本**，`python3`/`python3.12` 等别名成为 exec 它的**真实脚本**（不是三份 60 MiB 副本），其余符号链接替换为所指内容，venv 的 `lib64 -> lib` 布局链接删除（`lib/pythonX.Y/site-packages` 才是真路径）。之后整树再扫一遍：仍存在符号链接即报错，而不是「先发布再说」。
5. **发布后验证**（沙箱，**无网络**）：发布 → **在发布后的真实路径上**运行 `<发布树>/bin/python` → 要求它报告 `sys.prefix == 发布路径`（这是「迁移后仍可用」的证明）、解释器版本等于计划、已安装集合逐项等于锁定集合 → **才切名字**。验证失败时名字不动，已发布但未命名的内容保留为可核查结果（`env verify`/`list` 看得到），因此不会出现「名字指向跑不起来的内容」。

**计划身份是锁，不是内容**：内容 digest 在构建前不可能知道，假装知道等于让人批准没见过的东西。因此计划记录 `state/environment-provision-plans/<锁digest>-<名字>-<回合>.json` 保存解释器、来源、每个包的版本与**全部候选 digest**、完整锁定文本、影响范围，以及当时名字指向的编号与版本；执行前只复核**名字**（内容由哈希锚定，无从漂移）。它与「发布一个已准备目录」的计划是**两个不同的对象**，只读投影也分开（`GET /environment-provisions`）。批准仍然是原生表单，且批准**永远不是工具参数**；取消/超时记为 `Refused`，失败记为 `Aborted{原因}`，待批计划不会自动重放。

**验证口径（2026-10-10，A183）**：离线形态（源是 wheel 目录）与**联网形态**都在默认回归里跑真实链路；联网形态用本机 PEP 691 索引 fixture（真 HTTP、真 JSON、真摘要）覆盖"解析 → 抓 HTTP → 离线构建 → 发布 → 验证"，并另有 opt-in 的**真实 PyPI** 端到端（`ANCHOR_ENVIRONMENT_LIVE_PYPI=1`，实测 `idna==3.7` 从 pypi.org 解析、从文件站下载、校验哈希、无网络沙箱构建、发布后 `import idna` 打印 `3.7`）。索引答 HTML（PEP 503）时解析能过、抓取明确拒绝并说明需要 PEP 691；索引给的字节与摘要不符时拒绝且不留残留文件。**真实部署已验收（2026-10-10，A184）**：宿主带着这套配置真的启动过，并走完「管家登记需求 → 原生表单 → 人确认 → 抓取/构建/发布 → 图绑定并真的用它跑完一个 Run」整条人机路径，证据见 `.local/env-deploy/evidence.json`。

**已知边界（阶段边界，不缩减完整管家目标）**：①只安装目标平台兼容、已锁定 hash 的 **wheel**；不编译 sdist（`--only-binary :all:` 在解析阶段就拒绝纯源码源；抓取层再拒绝一次）、不装系统库、不做跨机器分发；②解释器必须 **3.8+**，且其 prefix 必须在 Run 沙箱本来就挂载的系统目录下（`/usr`、`/bin`、`/lib`、`/lib64`、`/sbin`）——否则环境在这里能建、在 Run 里跑不起来，所以在**解析阶段**就拒绝；计划记下 prefix 与 digest，作为「这是哪一份解释器」的事实；③索引必须是 PEP 691 JSON（PyPI 与主流实现都支持），HTML 简单索引未实现；④源白名单由部署给定，模型只能请求解析；⑤需求被满足的 `progress` 仍由名字表派生（发布即 `provisioned`），没有单独的「通知申请人」这一步，也没有记录清理策略；⑥已发布内容的写保护仍靠部署加固（不同所有者/只读挂载），`chmod` 只是信号；⑦uv 的 bootstrap digest 由部署提供并在使用前复核，但**首次安装 uv/解释器本身仍由部署包负责**。
