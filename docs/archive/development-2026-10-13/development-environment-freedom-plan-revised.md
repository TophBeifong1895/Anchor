## 1. 方案结论与已认可的选择

建议为 Pilot 提供 **Session 内每项目一份私有、可变的 Python 开发环境，引用 Host 的共享只读解释器**。Pilot 使用普通 pip 和项目文件组织开发；正式候选与已安装 Plugin 继续独立准备和执行。

本方案替换原稿的立论和实施顺序。开发自由成立的依据是私有字节、执行隔离、项目协调和独立候选验证；源码摘要只负责代码身份，不能单独证明测试成功或测试与安装的依赖环境一致。

| 决策事项 | 本方案的选择 |
| --- | --- |
| 开发环境的归属 | Session 持有项目现场；每项目一个稳定环境，不建立可发布的环境资产或历史环境版本 |
| 开发依赖的操作方式 | 支持空环境、pip 安装/升级/卸载、editable、console script、requirements 和 pyproject；沿用标准工具语义 |
| 声明与现场的关系 | 项目文件是重建基线，当前环境允许偏离；默认准备不静默同步或清除试装包 |
| 开发取包策略 | 在冻结的任务网络和沙箱授权内使用 pip；不承诺 Host 统一来源和强制哈希保证，需明确修订标准的适用范围 |
| 正式交付承诺 | 保留现有确认、代码摘要和正式取包校验；不把它描述为已强制绑定成功测试结果。本专项不新增强制测试绑定门禁 |
| 并发与恢复 | 同项目准备和命令串行；取消后核查实际环境，必要时显式重建，不保留历史环境来伪装自动恢复 |
| 删除与旧现场 | Pilot 删除项目时释放其私有环境；Session 删除统一清理。旧视图保留兼容，切换不得偷偷删除旧现场或解除候选引用 |

这里涉及开发准备语义、临时资源归属和标准适用范围的变化，不能称为“只改目录、所有不变量一行未变”。以上选择已获用户认可，按后文契约实施与验收。

这些事实说明应当拆开开发与正式运行的职责，也说明原稿“不可变性在开发路径不产生保护”“源码摘要已经保证测过即发布”的表述需要撤回。

## 3. 为什么开发环境不需要版本化身份

现有不可变视图的理由是硬的：一个进程只能看到同一个包的一个版本，所以多版本共存只能靠"一进程一视图"。这条推理没有问题，它是正式视图和候选视图正确使用不可变性的原因。

问题在于：**开发路径从不需要"两个版本同时存在"**。开发的性质是反复改主意——换一个 pytest 版本、加一个 requests、试完删掉——任意时刻只需要一个版本。开发路径付了"多版本共存"的全部成本，却从来没用到这个功能。

这引出一个更根本的判断：**干净不等于不可变，干净等于环境里不存任何无法从"声明＋可获取的安装来源"重新推导出来的事实。**

一个环境如果是纯投影，它可以随时删除、随时重建，它永远不产生需要人工回收的资产，因为它从来不是真相本身。反过来，一个不可变但没有用户的环境，一旦被引用保护，就成了"被保护的垃圾"——占着空间，但没有任何人需要它。

这就是私有开发环境"无版本身份"的根本理由，不只是设计偏好。**可丢弃性来自"不存无法推导的事实"，而不来自"不可变"。** 两条路都能产生可丢弃的环境，但代价不同：不可变路径的代价是每次改主意就长出一个新目录，私有拷贝路径的代价只是磁盘上多一份 CoW 拷贝。

修订稿第 2 节已指出"源码摘要已经保证测过即发布"的表述需要撤回——这是正确的。但撤回这条表述不意味着开发环境需要版本化，它只意味着"测过即发布"这个更强的承诺需要额外的测试绑定门禁（见第 8 节），而那是另一件事。

## 4. 目标、边界与事实所有者

### 用户可见目标

- 无第三方依赖也能先建立项目环境，然后自由试装包。
- `anchor_run(project=...)` 下裸 `pip`、`python -m pip`、Python 别名、shell 和 console script 使用同一个项目环境。
- 支持 `src/`、`pyproject.toml`、`pip install -e .` 和 `pip install -e '.[dev]'`；源码修改无需重新取第三方包。
- requirements、pyproject、约束和锁文件由项目自己维护；开发和测试依赖不自动写入正式 `plugin.json`。
- 不同项目默认安装到各自环境，包版本互不混用；开发修改不改变候选和已安装 Plugin 的依赖字节。
- 项目环境可继续使用、检查、显式重建和释放；Session 删除不要求用户另行回收一项环境资产。

### 能力与事实归属

| 内容 | 所有者与契约 |
| --- | --- |
| 基础解释器、固定 uv、引导工具和来源配置 | Host 的现有 `RuntimeConfiguration`；当前 Turn 冻结的解释器保持有效 |
| 正式 Plugin 代码、包存储、正式视图 | Library；继续按 Plugin 声明准备，下一次节点调用读取当前正式 Plugin |
| 正式候选及其临时视图引用 | 现有候选用例与开发 scope；继续只读并受有效引用保护 |
| 项目源码与声明文件 | Session 工作区；由 Pilot 用现有文件工具和命令维护 |
| 私有开发环境 | Session 项目现场；路径由 Host 派生，包字节可写，不进入正式资产或 Run 环境绑定 |
| 归属、项目锁、解释器绑定及必要准备状态 | Host 保存最小事实，不让项目可写目录成为授权来源 |
| 命令、文件、网络、进程和取消 | 现有 Sandbox 与 Host 授权；模型参数和包的构建脚本不能扩大权限 |

“没有环境版本身份”只表示不再按求解结果保存多份项目环境。owner、Session、项目和冻结解释器仍必须可核对。

本专项面向 Pilot 项目命令，不为 Graph 增加环境声明，不改变 AgentNode/OpNode 的准入契约、Kernel、Goose 会话、Run 格式或正式 Plugin 热更新语义。也不新增环境市场、通用依赖管理平台、恢复引擎或包管理器。

## 5. 私有环境的隔离与装配

### 5.1 存储关系

```text
Host 共享解释器 ──只读引用──> 正式视图 / 候选视图 / 私有开发环境

Library 共享 store ──只读指针──> 正式视图 / 候选视图

经验证的安装来源 ──标准安装、私有字节──> Session 项目环境
任务授权内的 pip 获取 ──标准安装、私有字节──> Session 项目环境
```

共享 store 中每个包版本仍只有一份正式存储。私有开发副本是 Session 草稿，不成为第二套发布存储，也不直接回填 store。共享解释器不复制、不改写；项目 venv 引用它。

私有包不得与共享 store 使用 hardlink。可使用具有写时分离语义的 reflink/clone，失败时退回普通 copy。正确性不依赖 reflink，空间收益单独测量。

### 5.2 装配优先使用标准安装器

复用固定 uv、现有经验证 wheel 缓存和基础解释器建立真实 venv。需要明确 `pip` 的引导来源及版本：可利用已核验解释器携带的 `ensurepip`，或从 Host 授权来源准备私有 pip；二者都不能向共享解释器安装包。

不直接解引用复制整份旧 `PreparedView`。原视图的 launcher、解释器链接、安装元数据和目录合并方式服务于共享存储；必须保证新环境中的 shebang、console script、`RECORD` 和卸载布局均指向私有安装。

准备过程与后续执行应使用一致的沙箱环境路径，避免在 Host 临时路径生成脚本后换挂载路径，导致入口失效。已有只读基础挂载、精确可写挂载和命令解析能力优先复用。

**离线兼容边界：** 当前路径可在仅剩解包 store、wheel 缓存已删时继续准备视图；普通安装器通常需要 wheel。首个切片必须单列此场景并确定复用方式，不能假定标准安装器无损替代。方法未验证前，保留旧视图能力，不将仅剩 store 的私有环境重建写成已支持。

### 5.3 执行时不挂共享 store

Host 装配过程可以只读访问必要来源；它与 Pilot 项目命令使用不同的授权集合。项目命令只获得自己的私有环境、原有工作区/明确输入和只读解释器，不获得 store、其父目录或候选环境的可写挂载。其他 Plugin MCP 的只读依赖挂载也不能直接复用给项目命令。

环境应放在 Host 所有的 Session 开发目录，位于 Library 开发引用扫描之外，并与源码候选目录分离。只挂具体项目环境，不挂包含兄弟环境、锁、归属事实或 Goose 历史的父目录。沙箱中采用稳定路径，例如 `/development/env`；具体内部目录名由实现按已有归属机制确定。

`PATH` 前置该环境的 `bin/`，设置 `VIRTUAL_ENV` 并保留 `PYTHONNOUSERSITE=1`。直接 Python 别名、裸 pip、`python -m pip`、shell 内命令和新生成的 console script 均需实际验证。共享解释器的绝对路径仍受原有只读授权，不能通过调用它取得共享环境写权。

隔离验收不能只查 symlink：应从命令沙箱直接访问已知 store 绝对路径并验证不可见，同时检查入口脚本不依赖 store，尝试向共享解释器及正式视图写入并验证拒绝。editable 的项目内路径和解释器 symlink 本身可以存在。

pip 构建后端、`.pth` 和项目代码都视为普通获授权代码，只能在命令沙箱中执行。Host 不在沙箱外运行项目环境里的 Python 来读取元数据或判断环境状态。

## 6. 项目准备、声明与命令的行为

### 6.1 默认准备只确保环境可用

建议沿用 `development_prepare`，允许只传 `project`，并支持显式的 `ensure`、`rebuild`、`discard` 动作。字段命名可在实现时沿现有 schema 收敛，以下行为需固定。

| 动作 | 明确行为 |
| --- | --- |
| `ensure`，默认 | 新项目无环境时创建空 venv 并准备私有 pip；已有私有环境核对归属、基本布局和冻结解释器后复用，核对失败返回诊断。旧项目默认沿第 9 节继续用旧视图。既不自动同步声明或清空现场，也不声称依赖已验证 |
| 显式依赖安装 | Pilot 通过 `anchor_run(project=...)` 调用 pip，选择文件、包或 editable。工具返回实际结果，不将成功安装说成测试通过 |
| `rebuild`，显式 | 在项目锁下释放旧私有环境并重建空环境，保留源码与声明；工具只负责空环境与私有 pip，依赖由 Pilot 后续独立调用 pip 安装。旧视图按第 9 节保留。可能丢失私有环境内未写入声明的试装状态，不能由默认准备隐式触发 |
| `discard`，显式 | 在项目锁下释放该项目私有环境，不删除源码、正式候选、已安装 Plugin 或其引用。用于 Pilot 删除项目的工作流 |

默认准备结果只证明环境入口可用。当前包集合及可导入行为由实际 `pip list`、`pip check`、Python 命令和测试观察，不复用旧的不可变求解事实作真实性保证。

现有内联数组参数可保留调用兼容：传数组是明确的包安装请求，使用成熟安装器，不产生第二份长期依赖声明，也不隐式删掉未列出的包。文件与数组在同一次准备请求中争夺声明来源时明确拒绝。本项改变了原有“准备即完整视图”的语义，需同步工具描述和兼容说明；旧调用不应被静默当成精确同步。

### 6.2 普通项目文件与标准工具

Pilot 可以在同一项目上下文中执行：

```sh
pip install -r requirements.txt -r requirements-dev.txt
pip install -e .
pip install -e '.[dev]'
pip install --upgrade pytest
pip uninstall requests
python -m pip check
pytest
```

这里不规定 requirements 是唯一文件。项目可选择 requirements、pyproject 及锁/约束文件，Host 不复制它们成为新的声明资产。常见 extras、marker、续行、约束、递归 requirements 和本地 editable 交由标准工具在沙箱内解析，不扩展现有 Host 正式声明解析器来承担另一套 Python 项目语义。

工具入口中的 `project` 继续只接受工作区相对路径，拒绝绝对路径和父级逃逸。文件及递归引用只可访问沙箱已经授权的路径；外部 URL/VCS 取包仍受第 7 节的网络边界。传入文件不等于授权读取其引用的宿主路径。

### 6.3 安装、同步与重建分开

自由试装不会自动改写项目声明。`pip install -r` 沿用 pip 行为，不承诺删除文件中已移除的包。Pilot 需要删除依赖时，明确卸载；需要按基线恢复干净环境时，显式重建后重新安装。若已有获授权标准工具支持精确同步，可按其契约使用，但本专项不另写同步算法。

修改源码或声明文件本身不触发隐式安装、卸载或重建。可丢弃表示私有环境不作为正式资产保留，不表示可以无提示抹掉正在使用的现场。可重建表示能从仍可取得的声明、源码与安装来源重新准备；只有项目选择完整锁定等机制时才讨论严格复现，不承诺任意未固定版本的 pip 现场都可逐字节重建。

## 7. 网络、来源与哈希保证

建议明确区分两条路径：

| 路径 | 获取与权限保证 |
| --- | --- |
| Host 准备候选或正式 Plugin | 继续使用 Host 来源配置、公共地址/回环策略、归档哈希校验、离线构建和共享 store 发布规则 |
| Pilot 的私有开发命令 | 使用当前 Turn 冻结的任务联网授权及命令沙箱；允许正常 pip、本地路径和项目构建，不承诺统一来源白名单或强制哈希模式 |

第二条是对现行依赖标准适用范围的明确调整，不能只用“不改变网络模型”掩盖来源和哈希保证的差别。Host 的来源配置、共享 store、凭据和正式依赖校验不会因项目 pip 配置而改变。

建议审核后修订标准的不变量 3、8、11、12 的适用说明：正式和候选视图继续共享只读包，解释器继续共享只读；私有开发副本由 Session 管理，完整复制/安装后不承担共享 store 引用；普通开发取包遵守任务沙箱与冻结网络上限，候选和正式取包继续遵守 Host 来源及哈希规则。原有不变量 1、2、6、9、10、13 的产品含义保留。

无网不代表所有 pip 都必须失败：本地 wheel、源码和已具备构建依赖的 editable 可以成功。只有实际需要远端数据的请求才应因无网明确失败，不能回退宿主网络或旧授权。构建隔离所需工具缺失时如实报告；不通过临时扩大权限完成安装。

pip 与其构建代码能写当前命令已授权的工作区和私有环境。`--target`、`--prefix`、`--user` 不会扩大这些挂载权限；不能宣称 pip 只能写环境目录，因为工作区本来可写。不同项目“互不干扰”指默认环境与版本隔离；Pilot 原有的 Session 工作区权限仍然允许它显式编辑其他项目源码。

本稿不增加逐包审批或第二套联网确认。开发环境和包的存在不能改变 Turn 的权限快照，不能授予 Host 凭据、loopback 管理 API 或其他宿主目录。

## 8. 正式候选与交付保证

### 8.1 本专项保留现有交付契约

`plugin_prepare`、`plugin_test`、`plugin_install` 继续使用正式运行声明、候选 staging、原生确认和代码摘要复核。开发 venv、开发依赖、editable `.pth` 和绝对环境路径不进入正式 Plugin。候选测试不得借用私有开发环境，候选的 scope 引用和只读视图仍保留。

Pilot 在开发测试后整理独立候选，并实际准备、调用候选业务工具，核对返回的代码摘要、依赖集合和结果。独立候选运行失败就修正候选，不能复制整个开发环境绕过正式声明。测试只列出工具时，仍只证明协议启动，不冒充业务验证。

### 8.2 如实区分当前保证与更强目标

| 命题 | 当前能否作为机械保证 |
| --- | --- |
| 安装时使用用户批准且前后摘要一致的候选代码 | 有现行核对与私有快照机制 |
| 候选测试使用其所选准备事实和正式依赖 | 候选用例会核对代码及所选依赖视图；不借用开发 venv |
| 安装之前必须有一次成功业务测试 | 当前没有强制成功测试事实门禁 |
| 安装依赖一定等于此前测试依赖及解释器 | 当前没有该强制绑定；安装独立求解，包集合比较仅作为安装结果返回 |

本稿建议此次保持现有安装契约，收窄原稿“测过即发布”的机械保证表述。验收场景仍要实际完成候选业务测试、安装、正式调用，并核查本次事实；单个验收通过不代表所有安装都受强制测试绑定保护。

如果审核要求把“成功测试的代码、依赖锁及解释器组合”变成强制安装前置，应明确增加这一交付语义，保存最小测试事实并在安装前核对。它不是源码摘要自然推出的性质，也不作为本专项已经实现的前提；需另外收敛测试范围、重新求解和失效行为。

## 9. 并发、失败、清理与旧版本

### 同项目串行，不推断命令是否会改环境

私有环境准备、重建、释放和 `anchor_run(project=...)` 共用项目排他锁。Python 和 shell 均可能修改包，不能只给名为 pip 的命令加锁。等待锁保持取消能力；命令的子进程真正退出后才能释放锁。不同项目可独立执行。

scope lease 继续负责 Session 删除保护，不能代替项目锁。锁顺序沿现有 scope → project → 必要时共享依赖 writer 收敛；不持全局 Library 锁等待模型、用户或普通项目命令。

### 失败、取消和重启

环境创建失败不能发布“入口可用”事实；再次准备可修复或重建从未成功发布的创建残留。已经可用过的环境若布局损坏或解释器不匹配，默认 `ensure` 返回诊断，只有显式 `rebuild` 才能清空它。运行中 pip 失败/取消可能已经改写环境，返回真实错误和中断观察，不承诺回滚到旧包集合。Host 至少不能继续用旧准备收据宣称环境已验证。

恢复沿 Anchor 原有产品路径：保存实际工具与取消事实，让 Agent 检查 `pip check`、包列表、源码和测试后继续。Host 记录的未收束修改需触发现场检查；进程重启不自动重放 pip。没有调用过变更工具的任意环境也不因目录存在就被宣称依赖正确。

### 项目与 Session 清理

Pilot 删除项目时，通过同一项目用例释放私有环境，再用已有文件命令删除源码；不需要用户管理独立环境资产。单独在 shell 中删除源码目录，不等同于 Host 收到了资源释放请求，不能宣称此动作立即回收全部环境。遗留私有现场最迟在所属 Session 删除时统一清理。

Session 删除仍核对已有归属并阻止活动执行，释放候选/旧视图引用，清理所属私有环境和其他既有资源。已安装 Plugin 及其正式依赖保留。不能从任意目录消失推断候选或旧开发引用已经释放。

新私有环境不放入 Library 临时视图扫描，也不混入正式候选代码摘要。装配若读取共享 store，复制完成前须沿现有 writer/引用协调保证来源不被回收；完整私有化后不再持续保护来源。候选、旧视图和未知引用的保守回收规则保持有效。

Session 删除后，仅开发引用的共享包在引用释放后等待下一次成功回收；可复用现有触发点，不新建定时回收器，也不声称因此磁盘占用有界。

### 旧项目准备事实兼容

识别既有 `current.json`、不可变准备事实和引用登记，不能把旧视图直接挂成可写。已有旧项目的默认 `ensure` 继续返回并使用旧只读视图，明确说明私有 pip 尚不可用；不会仅因为调用了新版本工具而替换成空环境。

该项目首次明确调用 `rebuild` 时，创建新的空私有环境，成功后才保存 Host 所有的选择事实并切换项目命令入口；失败仍使用此前旧视图。旧文件和引用保留，后续依赖由 Pilot 明确选择文件并调用 pip 安装，不自动迁移。已经选择私有环境的项目，其默认 `ensure` 继续核查私有现场，不回退旧路径。新旧路径不混用，不将旧事实解释为新环境的健康证明。

切换后旧引用可能继续占用共享字节，直至所属 Session 明确释放；这是兼容成本，不能同时声称“所有旧目录已消失”。新的目录数量验收与旧 Session 的保留范围分别记录。

## 10. 实施顺序与验收

### F1：一个可运行的私有开发切片

合并原 D1—D3，并包含必要生命周期接入：空私有 venv、私有 pip、标准安装布局、Python/PATH/console script、editable、精确挂载、项目锁、取消后检查、候选引用隔离和 Session 清理。第一片不以“复制好了目录”作为交付。

| 验收 | 需要观察的结果 |
| --- | --- |
| 空项目与入口 | 无包请求可准备；裸 pip、`python -m pip`、Python 别名、shell 和 console script 使用同一项目环境与共享解释器 |
| 安装/升级/卸载 | 私有环境实际变化，import 和脚本正确；卸载后脚本及元数据按标准工具行为清理 |
| editable | `src/` 和 pyproject 项目可安装；修改源码后下一进程看到变化，既有 console script 正常 |
| 物理与权限隔离 | 私有包和 store 不共享 inode；改写/删除私有包后 store 内容、mtime 和 inode 不变；已安装 Plugin 继续通过确定性业务检查 |
| store 不可达 | 命令尝试已知绝对路径不可见；入口文件不依赖 store；shared prefix/正式视图写入被拒绝 |
| 项目版本隔离 | 两项目同包不同版本，各自 import 和 console script 正确；项目命令不挂兄弟环境 |
| 网络 | 断网时本地安装可成功，确需远端的请求失败；无宿主网络或旧权限回退 |
| 并发与取消 | 同 Turn 的同项目准备/命令串行；锁等待可取消；执行取消等待子进程退出，部分修改如实核查 |
| 引用与清理 | 新私有环境不阻断 Library 扫描；候选和旧引用仍保护共享包；删除开发 Session 后正式 Plugin 可用 |
| 失败与续聊 | 创建失败可重试；pip 中断后核查并继续，未把旧收据当成功事实，重启不自动重放 |
| **离线重建（阻塞条件）** | 当宿主只剩解包 store、wheel 缓存已删时，私有环境的重建行为必须取得一个明确结论：支持（给出实际可用的方式）或不支持（给出原因和降级策略）。**此项无明确结论不得关闭 F1。** 不能以最小 fixture 通过替代，不能标记为"后续再议" |

### F2：标准项目文件与可解释的重建

在同一私有环境中完成 requirements/pyproject 开发流程；覆盖 extras、marker、递归文件、约束和本地路径的标准工具行为及沙箱边界。修改文件后只有显式安装/同步动作改变环境；试装包保留、卸载和重建结果均可解释。旧内联参数的兼容行为有定向回归。

显式重建清除私有环境内未声明的试装状态，保留源码；重建工具成功只表示空环境可用。Pilot 后续独立调用 pip，从选定且可获取的基线安装，安装成败单独返回。完整锁定与未固定版本声明分别记录，不承诺二者同等复现。

### F3：正式交付与真实 Provider 验收

先用小型 fixture 和确定性 Provider 实际经过 Host、Goose ACP、授权 MCP、Sandbox 和 Library，证明私有开发与正式候选/Plugin 的隔离。跨模块切片收敛后执行一次必要 Rust 全量回归及 Clippy/fmt；Web 仅按实际改动验证。

再在隔离根用真实 Provider 完成一个小型任务：创建普通 Python 项目 → 准备空环境 → pip/editable 与一次源码修改重测 → 独立候选业务测试 → 原生确认安装 → 正式调用 → 删除开发 Session → 新 Session 再调用。记录实际代码、依赖、解释器和二进制身份，不用目录存在或工具表代替结果。

每个垂直切片分别记录接口接入、确定性回归和真实 Provider 证据；缺配置、跳过与失败明确区分。新私有环境未完成真实 Provider 闭环前，不将旧 A216 证据算作此方案已验收。
