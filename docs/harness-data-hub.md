# Harness 数据中枢：后续主方向

编制：2026-10-20。状态：**目标、判据和设计原则已经由用户确认，具体设计还没开始**。本文是后续工作的方向文档，不是任务书，也不授权实施。实施要另写任务书，涉及内核的变更要单独审查。

接手这个项目的 Agent 请先读第 1、3、4、11 节。遇到架构决定，先用本文判断它是否服务于这个目标。代码组织、可插拔边界和带验证门槛的推进阶段见 [总体架构](harness-data-hub-architecture.md)。

## 1. 目标

Anchor 是一个 Harness 系统。我们关心的不是某个具体业务做得好不好，而是 Harness 本身怎么运转、怎么变得更好。宪法迁移（见 [最终说明](anchor-runtime-migration-overview.md)）主要就是为这件事做准备。

最终要做到：运行数据统一落盘之后，用**算法**分析和总结这些数据，找出：

- 真正能提升任务质量和效率的 Anchor Harness、Graph、Plugin 的构建和组织方式；
- 针对不同性质的任务，最好的 Graph、Plugin 及其组合；
- Agent 的行为模式，以及 Agent 自己探索出来的、出人意料的好路线；
- Anchor 自身的架构缺陷；
- 我们提供给 Agent 的 Harness 还能怎么优化；
- 内核本身的问题，比如从不触发的规则就是删减候选，符合"减法优于加法"。

再往后，是通过算法让系统自己变好，也就是由算法驱动的 RSI。

**大模型分析只是起点，不是主力。** 让大模型 Agent 读数据、写结论，是最没有想象力的用法。主力应该是专门设计的分析工具和算法。大模型只是这些工具的使用方之一。

## 2. 评判依据

| 判据 | 说明 | 现状 |
| --- | --- | --- |
| 任务完成质量 | 最重要，但很主观，暂时没法构建梯度 | 只有间接信号：最终结局、人工介入（stop、resume、abandon、恢复决定）、放弃。人的评分属于宪法第五条所说"来自人的目的"，可以作为事实记录 |
| token 消耗量 | 每一轮模型调用的输入、输出、缓存 token 和费用 | `rust/anchor-runner-host/src/goose_acp/usage.rs` 已经在统计，但只写进节点的 evidence，没有进统一历史。内核的 `cost` 只是宿主传进来的一个 u64 |
| 时间效率 | 某个行为花了多长时间 | **没有记录**。内核的 Stamp 和测量点都没有时间 |
| 工具效率 | Agent 使用的工具接口的调用频率和成功率 | 只存在于 Goose trace（`goose_acp/trace`），不在内核历史里 |

此外还有不依赖业务语义的信号：被拒绝的提交及原因码、未知效果、迟到结果、版本冲突、停滞。

**不使用模型的自我报告**（宪法第四条）。所有数字都由宿主观察和盖章。大模型对质量的评判可以作为一种信号，但必须标明来源，不能当作权威事实。

## 3. 已确定的决定（2026-10-20，用户确认）

1. **时间必须记录。** 用户认为这是非常重要的指标。
2. **不设默认预算**（W4 由此结论）。只要模型还在正常工作就继续。内核里"超出预算就结算"的定律保留，只是默认不会被触发。怎么判断模型"不再正常工作"见第 10 节。
3. **真实 Provider、外部渠道实网和部署验收由用户负责。**
4. **所有事实走统一的 `Kernel::submit`，落成统一的 Record。** 见第 5 节。
5. **数据源是内核历史。** `points.jsonl` 只是有损摘要，不能用来把问题归到具体的 Graph 或 Plugin。中枢是可以随时丢弃、再从历史重建的投影，权威始终是历史。
6. **中枢只读，只提建议。** 分析结论如果要改变 Graph、Plugin 或配置，也必须作为一次提交，由人或 Validator 裁决（宪法第五条）。从第一天起就用围栏测试守住"中枢只读"。

## 4. 核心原则

1. **一切改变都是一次提交。** 只有一个写入口：`Kernel::submit`。
2. **提议和裁决分离。** 谁都可以提议，包括模型、人、代码和分析算法。是否接受由内核按规则裁决，身份、成本、时间都由宿主盖章。
3. **历史是唯一权威。** 状态视图、恢复信息、测量点、中枢的分析表，都是可以重建的投影。
4. **内核只懂形式，不懂语义。** 业务规则通过 Validator 插进来。内核只记录，从不根据时间、token 这些数值做裁决。
5. **事实优先于算法。** 算法以后可以慢慢开发，没记录下来的事实以后补不回来。所以先定"记什么"，再定"怎么分析"。

## 5. 统一提交：所有事实怎么进同一个接口

内核的数据结构本来就是通用的，见 `rust/anchor-kernel/src/model.rs`：

- `Resource`（:262）：`task` 字段可选，`state` 是任意 JSON，所以资源不一定是 Run；
- `Submission`（:70）：`content` 和 `evidence` 是自由内容，内核不解读，交给 Validator；
- `Action`（:46）：已经有 `Execute`，含义是"对外部世界产生效果"；
- `Validator`（:403）：按资源种类安装，新增一种数据只需新增一个 Validator；
- `Record`（:314）：每条由三部分组成：宿主盖的章（Stamp）、提交内容（Submission）、裁决结果（Verdict），另外可能附带提交后的资源状态。这就是统一的数据结构。

各类事实的落法（资源命名只是示意，具体在设计阶段确定）：

| 事实 | 资源种类 | 动作 | 内容 |
| --- | --- | --- | --- |
| Run 的变化 | `run/…` | 已有 | 已有 |
| 工具调用 | 每个 Run 单独一个效果资源 | Execute，结果另作一次带 evidence 的提交 | 工具和 Plugin 的版本、参数形状摘要、宿主看到的成败与错误类别、耗时 |
| 模型一轮对话 | 同上 | 每轮一次 | token、费用、首 token 时间、模型和参数 |
| Graph 保存、Plugin 安装 | `graph/…`、`plugin/…` | Write | 摘要和版本。这同时把细腰扩展到 Graph 和 Plugin |
| 人对质量的评分 | 评分资源 | Write，提交者是人 | 分数和标签 |
| 实验分配 | 实验资源 | Write | 某个 Run 被分到哪个变体 |

只有宿主能提交"观察"，Agent 伪造不了自己的成绩，"不信自我报告"这条原则由此自动成立。

注意事项：

- **粒度**：一次独立的效果或一轮对话记一次提交，不能每个 token 或每个流式片段记一次。每次提交都要加锁并写盘，开销要实测。
- **不和 Run 抢版本号**：观察类提交不能直接提交到 Run 资源上，否则 Run 的版本号会不停增加，并行节点之间会互相触发版本冲突。
- **历史体积**：每条 Record 可能附带提交后的完整资源。日志类资源的 `state` 要保持很小，主要内容放在提交的 `content` 里。
- **Goose 的工具调用目前只能事后看到**：工具在 Goose 内部调用。第一步先做事后记录；"先裁决再执行"需要在宿主侧拦截工具调用，属于后续的安全性升级。
- **读取不是提交**：查询和分析不改变任何东西，不走 `submit`。
- **不另写通用 Agent 日志**（[开发约定](../AGENTS.md#框架优先)）：中枢记录的是 Harness 层面的结构化事实（结构、版本、摘要、结局、成本、时间），不是第二份 Goose 会话。原始内容优先引用 Goose 原生会话，或者存进按摘要寻址的内容库，历史里只保留摘要。

## 6. 事实采集规范（第一优先）

从第 1 节的目标反推，算法需要以下事实。它们是设计的第一项工作：

| 目标 | 算法需要什么 | 现状 |
| --- | --- | --- |
| 什么配置能提升质量和效率 | 每条记录都能定位到完整配置：Graph 摘要、节点、Plugin 版本、模型和参数、提示词和工具集的摘要 | P1、P2 已补：观察事实带配置摘要，配置清单按摘要存储；Run 历史中的节点结果提交还没有盖配置摘要 |
| Agent 的行为模式 | 有顺序、有因果的轨迹：这次工具调用来自哪一轮对话，它的结果又引发了什么 | 顺序：同一资源内按历史的先后，跨资源按时间（P1 已补）。因果：P2 已记录天然标识，包括 `messageId`、`toolCallId`、第几次模型请求，以及 invocation 键 |
| 出人意料的好路线 | 能比较轨迹的相似度，从罕见的轨迹里挑出结局好、成本低的 | P2 已补动作抽象：工具名、参数形状摘要、失败类别 |
| 架构缺陷 | 实际执行流程和 Graph 设计之间的偏差：意外的循环、从不经过的节点、瓶颈 | 需要时间和因果 |
| 可靠的因果结论 | 受控变化：每个 Run 被分到哪个变体，这个分配本身也要记成事实 | **没有** |
| 复盘和离线评估 | 拿同一条历史，换一个配置重放，看在哪里分岔，类似编译器里的 bisect | 需要能取回模型原始响应，按摘要引用 |

**内核只需要记录宿主盖章、提议方无法伪造的东西**（P1 已完成，C1 重新冻结）：

1. **时间**：由内核的时钟盖章；
2. **配置摘要**：由宿主盖在提议者的身份上；
3. **资源的创建时间和配置**。

**因果关系不进内核。** 一个内核既不校验、也不解读的字段，按定义就是内容。因果用天然标识写进提交的 `content`。

**记录也不需要编号。** 历史只追加，记录在历史里的位置就是它在本资源内的顺序；跨资源的顺序看时间。P1 第一版加过全局序号和内核层的因果引用，审查发现它们带来了启动扫描、"一条历史坏了整个 Host 起不来"、删除后编号重复等问题，后来都删掉了，见 [P1 验证](../experiments/harness-hub/p1/verification.md)。

其余事实都由各资源的 Validator 和提交的 `content` 承载，不改内核。Anchor 还没上生产，旧历史不需要迁移。

## 7. 分析工具：轨迹代数

中枢第一层是一个投影器：读所有资源的历史，展开成统一的事实表，每次提交一行。列包括时间、组件、资源、在本资源历史中的位置、提交者、动作、裁决、原因、成本、耗时、配置摘要，以及从内容里解析出的因果标识。

在这之上，提供一套专门的分析接口，作为一等公民，而不是让人或模型每次从头写查询。例如：

- 筛选轨迹：按配置、时间段、结局、任务特征；
- 对齐、比较两个 Run，或两组 Run 的差异；
- 挖掘频繁的动作片段；
- 从轨迹还原实际流程图，并和设计的 Graph 对比；
- 比较两个变体的判据分布；
- 把结局归因到具体的步骤。

算法直接调用这些接口；大模型 Agent 通过 MCP 使用同一套接口；需要临时探索时，也可以把事实表导出给通用的 SQL 工具。所有接口都只读。

## 8. 算法路线

这些都是已有的成熟方向，不需要从零发明：

- **流程挖掘（process mining）**：从事件日志还原实际运行的流程，和设计的 Graph 对比，找偏差和瓶颈。最适合用来找架构缺陷。
- **序列模式挖掘、对比挖掘**：找出成功和失败的 Run 各自高频出现的动作片段，用来总结 Agent 的行为模式。
- **新颖性检测**：从罕见轨迹里挑出结局好的，用来发现出人意料的好路线。
- **多臂老虎机、贝叶斯优化**：在 Graph、Plugin 的变体和配置参数之间做受控搜索，就像编译器参数自动调优。
- **进化搜索**：以 Graph 结构本身为搜索对象，适应度由第 2 节的判据计算。这就是算法驱动的 RSI 环，对应宪法第四条后半句"只有被选择的改变才会留下"。
- **信用分配**：失败该归因到哪一步，用重放加局部替换做反事实对比。

前三类只需要观察数据，可以先做；后三类需要受控实验和足够的数据量。

## 9. 建议顺序

[总体架构第 11 节](harness-data-hub-architecture.md#11-推进顺序与验证门槛) 把下面的顺序细化成了带验证门槛的阶段，并在最前面加入噪声测量，在中间加入评测任务集；两者不一致时以总体架构为准。

1. **事实采集规范**：把第 6 节写成具体的字段、资源种类和 Validator 设计。
2. **内核变更**：时间、配置摘要、创建事实和只读读取。已完成（P1），因果关系改为写进内容。
3. **接入新资源种类**：工具调用、模型对话、评分、实验分配，按第 5 节的注意事项实测开销。
4. **投影器和最小体检报告**：放在独立的 crate 里，只读历史；按配置切分，输出第 2 节的判据，加上停滞检测和内核规则触发统计。目的是验证统一格式确实能支撑分析。
5. **轨迹代数接口**，以及流程挖掘、对比挖掘这两个最早可做的算法。
6. **把细腰扩展到 Graph、Plugin 保存和 Session 投递**：作为单独的迁移任务。
7. **积累真实数据后建立选择环**：受控实验、老虎机或进化搜索，选出的改进作为提交，由人或 Validator 裁决。

## 10. 已知难点与待决事项

- **停滞判断**：不设预算之后，需要一种不依赖业务语义的方式，判断模型已经不再正常工作，比如连续多次提交被拒、长时间没有新的提交被接受、同一个工具连续失败、反复执行同样的动作。建议先只提醒、不自动停，要不要停由人决定。
- **"任务性质"本身带语义**：要么只用结构特征（触发来源、输入形状、Graph 拓扑），要么由人给任务打标签。
- **相关不等于因果**：历史数据只能提出假设，"A 比 B 好"要靠受控实验证明。
- **还没有真实数据**：开发数据已经重置，确定性 Goose 测试的数据没有统计意义。中枢的价值取决于真实运行积累的数据量。
- **细腰目前只覆盖 Run**：Graph 保存、Plugin 安装和 Session 投递还不是内核提交。
- **待用户决定**：
  - history、`points.jsonl` 和内容库的保留策略，见 [M5 待决清单](../experiments/constitution-host-preflight/final/measurement.md#迁移后待决清单)；
  - 和 [`anchor-rsi`](rsi.md) 的关系：它要么就是中枢，要么是中枢的使用方，只保留一套系统。

## 11. 接手须知

- 任何持久事实的设计，包括提交、Stamp、历史字段、测量点和保留策略，都先问一句：**它是否让第 1 节的算法有数据可用。** 漏记的事实以后补不回来。
- 不要把语义放进内核，不要让内核根据时间、token 这些数值做裁决。
- 不要让中枢直接写入；所有改进都作为提交提议。
- 不要按 token 或流式片段记提交；不要用模型的自我报告；不要把大模型的结论当成权威事实。
- 不要另写一套和 Goose 会话重复的通用 Agent 日志。
- 本文的状态和顺序变化时直接更新本文；实施细节写进各自的任务书和验收产物。
