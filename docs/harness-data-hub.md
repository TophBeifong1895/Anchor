# Harness 数据中枢：后续主方向

编制：2026-10-20。状态：**方向已确定，设计未开始**。本文记录方向和已经想清楚的要点，不是任务书，也不授权实施。

## 为什么

Anchor 是一个 Harness 系统。我们关心的不是某个具体业务做得好不好，而是 Harness 本身怎么运转、哪里需要优化。

宪法迁移（见 [最终说明](anchor-runtime-migration-overview.md)）就是为此做的准备。现在 Run 的一切变化都要经过 `Kernel::submit`，历史统一落盘，并且每次裁决都会产生一个测量点。有了统一的数据格式，才能把所有运行数据放在一起做综合分析。

## 要做什么

建一个数据中枢，只看 Harness 层面的数据，把业务语义全部剔除。通过它可以：

- 做各种分析和总结，包括现在还没想到的；
- 自动发现问题：Anchor 自身的、某个 Graph 的、某个 Plugin 的；
- 把内核本身也当作分析对象；
- 以后进一步探索：针对不同性质的任务，什么样的 Graph、Plugin 及其组合最好。

## 已想清楚的要点

1. **数据源是内核历史，不是探针。**
   - `points.jsonl` 是一个有损摘要：不记录 Graph 摘要（`graph_digest`）、节点和 Plugin 版本，所以没法把问题归到具体的 Graph 或 Plugin 上。
   - 中枢的第一层是统一事实表：每条提交一行，被拒绝的也算，并带上 Graph 版本、节点、Plugin 版本、提交者、动作、裁决、原因和成本。
   - 中枢只是可以随时丢弃、再从历史重建的投影，权威始终是历史。
2. **质量信号不依赖业务语义。** 可用的信号有：
   - 结局：完成、失败或放弃；
   - 人工介入：stop、resume、abandon、恢复决定；
   - 被拒绝的提交及原因码；
   - 未知效果、迟到结果、版本冲突；
   - 预算耗尽；
   - 成本；
   - 耗时，前提是决定"时间是否作为内核事实"。

   不使用模型的自我报告，这一条来自宪法第四条。
3. **内核分析自己。** 统计每条裁决规则的触发次数。从不触发的规则就是删减候选，符合"减法优于加法"。
4. **中枢只提建议，不直接改动。** 分析结论如果要改变 Graph 或 Plugin，也必须作为一次提交，由独立的裁决者决定（宪法第五条）。从第一天起就用围栏测试守住"中枢只读"。

## 已知难点

- **"任务性质"本身带语义。** 要么只用结构特征（触发来源、输入形状、Graph 拓扑），要么由人给任务打标签。人给的标签属于宪法第五条所说"来自人的目的"。
- **相关不等于因果。** 历史数据的对比只能提出假设。要证明"A 比 B 好"，需要受控对比，测量点里的 `knobs` 字段就是为此预留的。
- **还没有真实数据。** 开发数据已经重置，确定性 Goose 测试的数据也没有统计意义。中枢的价值取决于真实运行积累起来的数据量。
- **细腰目前只覆盖 Run。** Graph 保存、Plugin 安装和 Session 投递还不是内核提交，它们的改变不会被测量。

## 建议顺序

1. 先做最小的"Harness 体检报告"：
   - 放在独立的 crate 里，只读现有的内核历史；
   - 按 Graph 版本和 Plugin 切分，输出第 2 点里列出的信号；
   - 不新增事实，不改内核。

   目的是验证"统一格式确实能支撑分析"。
2. 确定和 [`anchor-rsi`](rsi.md) 的关系：要么它就是中枢，要么它是中枢的一个使用方。只保留一套系统。
3. 决定"时间是否作为内核事实"，以及 history 和 `points.jsonl` 的保留策略。这两项决定都直接影响中枢能做什么，待决项见 [M5 待决清单](../experiments/constitution-host-preflight/final/measurement.md#迁移后待决清单)。
4. 积累真实数据后，建立选择环：受控对比，选出更好的一方并保留。对应宪法第四条的后半句"只有被选择的改变才会留下"。

## 用法

今后遇到架构决定，比如保留策略、时间事实、测量点和历史里记哪些字段、是否把细腰扩展到 Graph 和 Plugin，都先问一句：它是否服务于这个中枢。
