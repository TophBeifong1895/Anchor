# P6 实验 1：修复三处工具接口缺陷

方案在运行之前写定，判定规则不在看到结果之后修改。背景见 [P4 报告](../p4/report.md#新发现的-harness-缺陷由中枢的工具统计发现)。

## 假设

P4 的基线数据里，约 4% 的工具调用失败来自三处 Harness 缺陷：

1. `anchor_read` 和 `anchor_edit` 不接受 `/workspace/...` 路径；
2. 这两个工具的错误信息写的是 `anchor_run`，给的也是 `anchor_run` 的用法；
3. AgentNode 里公开了只在 Pilot Session 可用的 `project` 参数。

修复后，工具失败率下降；每次失败省下的那一轮模型请求，可能让时间和 token 略有下降；质量不变。

## 两组

| 组 | 代码 | 差别 |
| --- | --- | --- |
| A（对照） | 提交 `1af26b1`：只增加了配置清单里的 Host 摘要和工具定义摘要 | 无 |
| B（变体） | 提交 `5773aa3`：A 加上三处修复 | `anchor_read`、`anchor_edit` 接受 `/workspace/<path>`，其余部分照常检查；这两个工具的错误信息报自己的名字和用法，失败类别不变；`project` 只在可用时公开 |

两组都是同一台机器上编译的 debug Host（A 的摘要以 `d10438cc` 开头，B 以 `3d8b09e3` 开头），用同一个 Goose、同一个渠道和模型（平台默认 Flash）。每个 Run 的配置清单里都记有 Host 摘要，中枢靠它区分两组。

## 运行

- **任务**：P4 的精确档 9 个，加上 triage，共 10 个。fleet 一次要 4 到 10 分钟、波动大，并且可能超时，这次不跑。
- **次数**：每组每个任务 10 次，共 200 次。
- **顺序**：每一轮里，每个任务两组各跑一次；先跑哪组按"轮次加任务序号"的奇偶交替，让时段漂移平均地落在两组上。串行运行，同一时间只有一个 Run。
- 运行器看门狗中止的 Run 不评分，单独计数。

## 判定（中枢 `anchor-hub contrast`，按 `host_sha256` 分组）

- **主要指标**：全部工具调用的失败率，用两比例检验。B 显著更低（p < 0.05）才算假设成立。
- **约束**：每个任务 B 的平均分比 A 低不超过 0.05，即 `contrast_quality_loss` 不出现。
- **次要指标**：每个 Run 的 Agent 用时和 token，先除以该任务 A 组的均值，再跨任务合并做 Mann-Whitney 检验。不要求显著，但 B 不能显著更差。
- **决定**：主要指标成立、约束满足、次要指标没有显著变差，就采纳 B。

## 结果（2026-10-21，运行之后追加）

200 次运行全部结束，没有触发运行器看门狗。下面的数字全部来自中枢：`anchor-hub contrast --reference d10438cc .local/harness-hub-p6/exp1`，原文见 [experiment-1-contrast.json](experiment-1-contrast.json)；原始数据在 `.local/harness-hub-p6/exp1/`，不入库。

### 主要指标：工具失败率，假设成立

| 组 | 工具调用 | 失败率 |
| --- | --- | --- |
| A | 1,310 | 6.1% |
| B | 1,246 | **0.8%**（两比例检验 p < 0.0001） |

按工具和失败类别看，三处缺陷造成的失败在 B 组全部消失：

| 失败 | A | B |
| --- | --- | --- |
| `anchor_read` 拒绝 `/workspace/...` 路径（`not_authorized`） | 13 | 0 |
| `anchor_edit` 拒绝 `/workspace/...` 路径（`invalid_arguments`） | 28 | 0 |
| `anchor_run` 因 `project` 参数被拒（`not_executed`） | 30 | 1 |

B 组剩下的 10 次失败是模型自己的失误：

- 5 次 `anchor_run` 漏传 `command`；
- 2 次往不存在的目录写文件；
- 1 次覆盖已有文件但没带摘要；
- 1 次命令不在允许列表里；
- 1 次 `final_result` 的回执不匹配。

### 约束：质量没有下降，满足

- 没有出现 `contrast_quality_loss`。10 个任务里，B 的平均分没有一个低于 A。
- 全对的 Run：A 93/100，B 97/100。

两组都出现的失分：

- contacts 两组各有 3/10 误读电话格式，和 P4 一致。

只在 A 组出现的失分：

- audit 有 1 次漏了 `short`；
- audit 有 1 次 Agent 没有调用 `final_result` 就结束，Run 停在等待人工，没有评分；
- incident 有 1 次时间错了；
- triage 有 1 次优先级错了。

A 组这几次失分在统计上不显著，不能据此说修复提升了质量，只能说质量没有下降。

### 次要指标：没有变差，有改善的趋势但不显著

| 指标（B 相对 A，各任务先除以 A 的均值再合并） | 结果 |
| --- | --- |
| Agent 用时 | 0.979（Mann-Whitney p = 0.20） |
| token | 0.930（p = 0.12） |

失败最多的几个任务，token 下降最明显：

| 任务 | token（B 相对 A） | 轮数（B 相对 A） |
| --- | --- | --- |
| routing | 0.77 | 0.84 |
| triage | 0.78 | 0.84 |
| audit | 0.86 | 0.91 |

每次失败少一轮模型请求，和这里看到的轮数下降一致。效果在每组 100 次的样本下还不显著；要确认 7% 这个量级的 token 下降，需要更多次运行。

### 决定

主要指标成立，约束满足，次要指标没有变差：**采纳 B**，即提交 `5773aa3`。

### 这次实验说明了什么

- 这是第一个完整闭环：中枢从 P4 的数据里发现问题，修复做成变体，在同一个任务集上受控比较，再由中枢判定。整个过程只用到已经落盘的事实，没有用模型的自我报告。
- 以质量为约束、效率为目标的判定方式可行。
- 这种 Harness 级别的小修复，最直接、最稳定的信号是工具失败率；时间和 token 的效应较小，需要更大的样本才能看清。

### 补记：两组共有的启动期开销

切片的完整 Goose 回归发现，提交 `1af26b1` 让 Host 在启动时计算自身可执行文件的摘要；debug 编译下 sha2 没有优化，算一次约 5.6 秒，导致 10 项测试超时。已由提交 `513cc8a` 修复：dev 配置里单独优化 sha2，计算降到 0.3 秒以内。

A、B 两组都基于修复前的代码，所以这个开销对两组相同：

- 摘要在后台线程计算，两组每次调用的记录耗时都是 39 毫秒，和 P4 相同；
- 两组的绝对耗时里可能都包含这段启动期的后台计算，但它不影响两组之间的比较，也不影响以工具失败率为主要指标的结论。
